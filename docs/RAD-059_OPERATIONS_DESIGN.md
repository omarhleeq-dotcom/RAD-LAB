## المسؤولية والقبول

المالك هو المستجيب الأساسي وصاحب SQL وGCP وقرار الاستعادة. لا بريد أو هويات مشاركين في Git. يختار لاحقًا مستجيبًا بديلًا ويتحقق من صلاحياته واستلامه. **حتى اختياره، التصعيد يعني إبقاء البوابة مغلقة**؛ غياب المستجيب أثناء نافذة امتحان يمنع فتحها. وصول البريد ليس ضمان حضور أو SLA.

بعد دمج #153 وإتمام تمرين المالك، تُسجل RAD-059 في review في [مصدر الحالة](project-status.md). تبقى قنوات الإنذار وتنبيه الميزانية واختبار الاستلام واختيار البديل مفتوحة؛ Supavisor cache ورفض الاعتماد القديم يحتاجان RAD-082. لا done أو إذن أول امتحان من نجاح التمرين؛ RAD-082 والحقوق/الخصوصية والمراجعات القائمة مستقلة. العامل يبقى NOLOGIN والسر DISABLED حتى قرار استئناف منفصل.

## إشارات الصحة والعتبات والاستجابة

SQL المراقبة المقترحة للمالك postgres في SQL Editor: READ ONLY، مخرجات تجميعية فقط، بلا أجوبة/نتائج/UUID/بريد أو نص استعلامات. health_v1 موجودة وتقرأ counts فقط، لكنها تمسح الجلسات كلها؛ لا نستدعيها آليًا أو نمنح worker إلى مراقب. الفحص المحلي الجديد يستعمل sentinel1001 للجلسات وAuth؛ عند تجاوز1000 أو مهلة الفحص لا ينتج أصفارًا مطمئنة. خطأ SQL يعني UNKNOWN، لا healthy. قراءة pg_database_size تخص حجم القاعدة لا مساحة Storage؛ تطابق Usage عند المالك هو مرجع الحصة.

## التكلفة: إيقاف التنفيذ فعليًا

الميزانية والتنبيه ليسا cap. التسلسل العملي: Pause لأي Scheduler موجودة، Cancel لكل execution جارية/معلقة في Job، معاملة DB للإغلاق/التجميد/NOLOGIN/الإنهاء، ثم Disable لكل إصدار رقمي يمكن للعامل الوصول إليه ضمن الربط المراجع. تحقق صفر executions عاملة وNOLOGIN وصفر backends والسر DISABLED. تعطيل السر وحده لا يسحب اعتمادًا محمّلًا، وNOLOGIN وحدها لا تقتل اتصالًا قائمًا. تظهر خطوات الهاتف وحالات الفشل في دليل التشغيل عند اكتمال المرحلة الثالثة.

| قرار | البدائل والتوصية |
|---|---|
| حدود Job | موصى tasks1/parallelism1/retries0/CPU1/memory512Mi/timeout300s، وbatch1/pool1. خيار زيادة السعة مؤجل لقياس مستقل؛ لا max-instances=0 لـJob ولا تغيير قالب يوقف execution بدأت سابقًا |
| Scheduler | موصى ABSENT؛ إن كانت موجودة PAUSED، retries0 وmaxRetryDuration0، لا إنشاء لاختبار Pause. التفعيل لاحقًا بعد حل التداخل وقياس الإيقاع؛ list-before-run ليست قفلًا |
| المبلغ | اقتراح5 USD شهريًا مع50/80/100% وforecast100%؛ المالك يختار المبلغ والمستلمين قبل أي تشغيل، ولا يعتمد التقرير صرفًا |
| وقف التكلفة | اختيار المالك: وقف تشغيل العامل مع بيان البواقي؛ صفر إنفاق المشروع يتطلب فصل Billing/حذف موارد بقرار مستقل قد يؤثر خدمات أخرى |
| Supabase | Free: DB500MB وStorage1000MB، لا provider backup/PITR. خيار مدفوع فقط بقرار مالك؛ RAD-082 للنسخ المحلي والاستعادة قبل أول امتحان |

قد تبقى تكلفة Artifact Registry وتخزين Secret Manager (حتى نسخة معطلة) والسجلات/الفوترة المتأخرة وScheduler المتوقفة. لا ندعي صفرًا نقديًا أو نزيل سجلات/صور/أسرار تلقائيًا. يراجع المالك Billing Reports حسب الخدمة، ثم يختار تنظيفًا مستقلًا للمراجع غير المستخدمة. لا يُستعمل guard0 لإثبات وقف الحوسبة؛ قد يبدأ التنفيذ ويستهلك قبل خروجه.

## S-STD-3 وحدود الحجم

مراقبة SQL كل5دقائق **يدويًا أثناء نافذة بحضور المالك فقط**، وقبلها وبعدها؛ Usage يوميًا. لا polling من الوكيل أو daemon. نافذة4ساعات تعني نحو48قراءة؛ لا نفترض مجانية CPU بلا حدود. sentinel1001 وstatement5s/lock2s يمنعان تقريرًا أخضر جزئيًا، لكن الفرز/الإحصاء قد يحتاج مسحًا أوسع مع نمو البيانات؛ أي timeout يوقف الاعتماد على المراقبة الحالية. أداة الإيقاف لا ترفض عدد جلسات/اتصالات معينًا، لكن مهلاتها قد تنتج PARTIAL مع حجم/أقفال كبيرة؛ يعالج المالك العائق ويعيد الإجراء دون افتراض نجاح.

حد التنبيهات المقترح لسياسات Monitoring الثلاث: افتتاح واحد وإغلاق واحد لكل حادث/سياسة، أي حتى6رسائل إذا فتحت السياسات الثلاث معًا ثم أُغلقت، دون تذكير دوري. رسائل budget وSupabase يتحكم بها المزوّد وقد تتكرر؛ ليست ضمن cap مضمون، يراجع المالك التواتر في تجربة الاستلام ولا يضيف مستلمين تلقائيًا. تصعيد بشري واحد بعد15دقيقة بلا استجابة؛ حتى اختيار البديل يعني ذلك gate مغلقة. حد GitHub الاختياري ساعة لا يناسب إنقاذ امتحان؛ الرصيد مشترك مع CI ويفحص قبل أي تمكين. السقف الحالي يدوي وهاتف واحد ودوران a/b؛ رافعه RAD-082 ومسار laptop/CLI مع النسخ والاستعادة. زيادة الحجم/الإيقاع أو الاعتماد على خطة مدفوعة قرار مستقل.
