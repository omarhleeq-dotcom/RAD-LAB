## 3. بريد التأكيد (SMTP) — نُفِّذ بـ Brevo (2026-10-15، المالك)

**ما اعتُمد فعليًا (S-PILOT-6):** Brevo (باقة مجانية، 300 رسالة يوميًا بحسب لوحتهم) بمرسل `radlab.pilot@gmail.com`. خطواته كما جرت، لمن يعيدها: (1) تحقق الهاتف في Brevo (شرط منهم قبل مفتاح SMTP؛ تعثر مرات قبل أن ينجح)؛ (2) Senders ← إضافة المرسل (يحذّر Brevo من العناوين المجانية فاختر Add this sender anyway)؛ (3) SMTP & API ← Generate SMTP key؛ (4) **Security ← Authorized IPs ← Deactivate for SMTP keys** (الحجب الافتراضي يمنع عناوين Supabase)؛ (5) في Supabase: Authentication ← Emails ← SMTP Settings: Host `smtp-relay.brevo.com`، Port `587`، **Username = «Login» الظاهر في صفحة SMTP & API (مثل `be…@smtp-brevo.com`) وليس بريد الحساب**، Password = مفتاح SMTP، Sender = بريد المرسل. **جُرِّب بدعوة حقيقية: وصلت إلى Inbox.** يرسل Brevo من نطاق تابع له (`…brevosend.com`) ويجعل `radlab.pilot@gmail.com` عنوان الرد. مفتاح SMTP ينتهي بعد 90 يومًا بلا استخدام. SPF/DKIM/DMARC لم تُفحص بعد (اختياري). **أسلم للتوصيل لاحقًا: نطاق خاص موثّق** (مدفوع، مؤجل).

> النص التالي كان قبل الاعتماد ويُترك للتوثيق: الخادم المدمج لا يصلح…

الخادم المدمج **لا يصلح**: «Send messages only to pre-authorized addresses» (أعضاء مؤسستك فقط)، وحده 2 رسالة في الساعة. المشاركون الخارجيون لن يصلهم بريد التأكيد بدونه.
المطلوب: خدمة إرسال بريد SMTP من اختيارك وإدخال بياناتها في Authentication → SMTP **(قد يختلف)**. لم أقرأ شروط أي خدمة بريد، فاقرأ حدودها المجانية بنفسك أو اطلب جلسة DOCS لمقارنتها. بعد الإدخال جرّب إرسال بريد تأكيد إلى عنوان **ليس عضوًا** في مؤسستك.

1. حدّد المشروع والبيئة بوضوح (local / staging / production)، الفرع وcommit، المسؤول الوحيد عن التطبيق ونافذة الصيانة. سجّل نسخة Supabase CLI الفعلية بـ`supabase --version` خارج الأسرار وثبّت **تلك النسخة نفسها** لجميع خطوات التجربة والتطبيق؛ لا تعتمد `latest` بينهما. لا حاجة لإضافة اعتماد npm أو مدفوع أو أسرار CI. إعدادات Auth/SMTP تبقى عملية المالك؛ أدلة وصول البريد في §3 محفوظة.
2. من checkout نظيف للـcommit المقبول، اعرض أسماء `supabase/migrations/*.sql` بالترتيب المعجمي وخذ `sha256sum supabase/migrations/*.sql` إلى سجل عملية آمن خارج Git يحفظ اسم الملف/البصمة/commit/المشروع/نسخة الأداة/المشغّل/الوقت الحقيقي/النتيجة. **لا تحفظ بيانات اعتماد أو dumps في هذا السجل أو Git.** قاعدة الترتيب: timestamp فريد من14 رقماً ثم اسم، ولا تعديل لملف مطبّق؛ التصحيح ملف لاحق. الاختبار الجديد يكتشف كل ملفات SQL تلقائياً؛ قائمة الخمسة في fixture هي تاريخ اختبار فقط.
3. **مشروع SQL Editor الموجود ليس مشروعاً جديداً:** اجرد الجداول/الأعمدة/defaults/الفهارس/FKs/CHECKs وسياسات RLS والأدوار/الأوامر/predicates، grants الجدول/الأعمدة/sequence/function وSECURITY DEFINER/search_path، والدالة/trigger على auth.users، وقارنها بكل ملف وببصمته من النسخة المقبولة. جرد أسماء فقط أو رسالة Success قديمة لا يثبت التطابق. افحص أيضاً `supabase_migrations.schema_migrations` بـ`supabase migration list` بعد اختيار المشروع الصحيح.
4. إن كان ملف مثبت التطبيق ومطابقاً لكن التاريخ غائباً، يمكن للمالك بعد اعتماد المسار وتصوير الجرد استعمال `supabase migration repair --status applied <timestamp>` للمشروع المحدد. **repair يعدّل ledger فقط ولا ينفّذ SQL**. لا تضع علامة applied لكل الخمسة بالتخمين، ولا تعِد تشغيل أول migration (فيه revoke واسع)، ولا تستخدم IF NOT EXISTS لإخفاء drift. إذا اختلف شيء: توقّف، سجّل الفرق وصمّم migration تصحيح مستقلاً قبل .1؛ لا تصلحه يدوياً خارج السلسلة.
5. في المسار المعتمد لاحقاً: `supabase db push --dry-run` أولاً؛ يجب أن تعرض الخطة الملفات غير المطبقة الصحيحة فقط بالترتيب. راجع الهدف والنسخة والبصمات والنسخة الاحتياطية والاختبار؛ ثم المشغّل الواحد فقط ينفّذ التطبيق. لا تغيّر مشروعاً أو تشغّل push أثناء وجود مشغّل آخر. لا تشغّل `db reset` على مشروع بعيد؛ reset للاختبار المحلي فقط. لا اعتماد على Supabase Branching المدفوع.

#### staging والذرّية والأقفال

- اختبارات CI تبني PGlite جديداً من **كل** الملفات مرتبة، مع محاكاة Auth/roles فقط، وتجرّب ترقية fixture الخمسة؛ ليست خدمة Supabase حقيقية. بعد ذلك يجرّب المالك على **مشروع Free ثانٍ متاح** ببيانات وحسابات اصطناعية فقط (يمكن تناوب staging وتجربة restore على المشروع الثاني). إذا كان المشروع مستخدماً فلا تمسحه أو تستبدله؛ انتظر مشروع تجربة متاحاً. لا تنتقل إلى الإنتاج بمجرد نجاح PGlite.
- للمشروع التجريبي يبدأ المالك من المخطط المعتمد ويطبق الملف السادس **مرة واحدة وفي transaction واحدة**. فهارس CREATE INDEX العادية transactional وتحجز الكتابات أثناء البناء؛ اختبر وقتها وحجمها وتعارض الأقفال أولاً. احتفظ بالفهرسة العادية لهذه الدفعة؛ لا تحوّلها إلى CONCURRENTLY داخل transaction. اختيار CONCURRENTLY لاحقاً يحتاج ملفاً/خطة منفصلة وإدارة فهرس INVALID وغير transactional.
- حدّ انتظار القفل ووقت statement باختيار مُختبر للبيئة (مثال أولي staging: lock_timeout=5s وstatement_timeout=60s، ليست ضمان زمن للإنتاج). إذا استُخدم psql كمسار SQL-editor-compatible، استخدم `--single-transaction --set ON_ERROR_STOP=1 --file supabase/migrations/20261020000100_scale_read_foundation.sql` مع الاتصال الذي يضبطه المالك محلياً؛ لا تُلصق اتصالاً أو كلمة مرور في chat. التشغيل المباشر لا يسجل ledger تلقائياً: بعد النجاح والجرد فقط تُسجل النسخة بما يوافق المسار المعتمد. اختيار CLI لا يعفي من التحقق من حدود transaction للنسخة المثبتة؛ اختبر فشلاً مفتعلاً في staging وتحقق أن فهرساً/default جزئياً لم يبق.
- عند خطأ/مهلة داخل transaction: ألغِها، تحقق من غياب آثار الملف السادس ثم عالج سبب القفل/الخطأ؛ لا تتابع من منتصف الملف. بعد COMMIT لا يوجد rollback تلقائي: أوقف التطبيق التالي، استخدم forward-fix مراجعاً؛ يمكن الإبقاء على الفهارس والـdefault الجديد أثناء التشخيص. إعادة predicates القديمة إن لزم تكون في ملف لاحق من النسخة المرجعية مع جميع شروطها وصلاحياتها؛ لا حذف CHECKs/سياسات أو إيقاف RLS. استعادة dump إجراء استرداد مستقل عند المالك، لا زر رجوع روتيني.
- قبل الإنتاج: نسخة منطقية مشفرة + تجربة restore وفق §8، ثم نافذة القفل والموافقة التشغيلية. تطبيق DB الإضافي قبل أي تطبيق عميل يعتمد عليه؛ هذه الدفعة متوافقة مع العميل الحالي والرموز القصيرة، ولا تحذف توقيع RPC الحالي. في الدفعة .2 احتفظ بالتوقيع القديم حتى خروج النسخ الساكنة القديمة. سجّل pre/post row counts، فهارس valid، predicates/grants/trigger، نجاح حالات العزل، وledger/البصمات والوقت الحقيقي. لا تُسجّل مجرد نجاح push كنجاح للتجربة الحية.

#### النسخ/الاستعادة وحدود الإثبات

S-PILOT-4 يفوض المالك بالنسخ المشفر وتجربة الاستعادة؛ لا نختار cadence/RPO/RTO أو مدة احتفاظ بالنيابة عنه (S-PILOT-15/19 مقترحان). افحص في استعادة **اصطناعية**: auth login وكلمة المرور/تأكيد البريد، رموز/status/consent، attempts/events/feedback وروابطها وsequences، RLS/grants والدوال/trigger على auth.users وتاريخ migrations. customisations للـauth/storage والتاريخ قد تحتاج معالجة منفصلة، وإعدادات SMTP/redirects ليست مجرد صفوف public. حدّث سياسة CSP لأصل مشروع التجربة محلياً عند الحاجة، دون فتح المعاينة أو تعديلها هنا. سجّل الطلبات المحذوفة وأعد تطبيقها بعد restore؛ النسخ وCSV والاستبيان لا يمحوها cascade تلقائياً. **O105 لا يُغلق من اختبارات PGlite أو قراءة الوثائق.** حفظ المحاولات/الملاحظات/الاستعادة حيّاً غير متحقق في هذه الدفعة؛ هذا لا يلغي دليل وصول البريد السابق (§3).

المراجع الرسمية لمسار العمل: [Database migrations](https://supabase.com/docs/guides/deployment/database-migrations)، [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)، [Backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)؛ قرأها تدقيق 047a بتاريخ2026-10-15. تحقّق من دعم flags وحدود transaction في نسخة CLI المثبتة قبل استعمالها؛ لم تُشغّل أدوات Supabase أو إنتاج في هذه الجلسة.

## 5. حساب المالك والموافقة على المشاركين

1. أنشئ حسابك بأي طريقة متاحة (Authentication → Users → Add user **(قد يختلف)**، أو بعد 041b من صفحة التسجيل). أكّد بريدك.
2. اجعله المالك (SQL Editor، يعمل بصلاحية عالية فلا يمنعه RLS):
   ```sql
   update public.profiles set role = 'owner', status = 'approved'
   where user_id = (select id from auth.users where email = 'بريدك@example.com');
   ```
3. الموافقة على مشارك (حتى تُبنى لوحة المالك في RAD-044):
   ```sql
   update public.profiles set status = 'approved' where participant_code = 'P-xxxxxxxx';
   ```
   (من SQL Editor. الدالة `public.set_participant_status` تعمل من تطبيق المالك لاحقًا لأنها تتحقق أن المستدعي مالك معتمد.)
4. الإيقاف: نفس الأمر مع `'suspended'`. الحذف الكامل لمشارك (طلب حذف، Q7): احذفه من Authentication → Users؛ يُحذف ملفه وكل أحداثه تلقائيًا (مُختبَر).

## 6. ربط الموقع (متغيران عامان فقط)

في GitHub: Settings → Secrets and variables → Actions → **Variables** → New repository variable:

|---|---|

## 8. النسخ الاحتياطي اليدوي واختبار الاستعادة (من لابتوبك)

الباقة المجانية: «Automatic backups: Not included in free». المطلوب نسخة منطقية بأدوات Supabase (صفحة backup-restore، قرأتها بتاريخ 2026-10-15):

1. ثبّت **Supabase CLI** و**Docker Desktop**.
2. من المشروع: **Connect** → انسخ سلسلة **Session pooler** واستبدل `[YOUR-PASSWORD]` بكلمة سر قاعدة البيانات (Database Settings إن نسيتها).
3. نفّذ:
   ```
   supabase db dump --db-url [CONNECTION_STRING] -f roles.sql --role-only
   supabase db dump --db-url [CONNECTION_STRING] -f schema.sql
   supabase db dump --db-url [CONNECTION_STRING] -f data.sql --use-copy --data-only
   ```
4. خزّن الملفات الثلاثة خارج GitHub في مكان مشفّر؛ تحوي بيانات المشاركين.
5. **اختبار الاستعادة قبل أول مشارك** (معيار الخطة §7): أنشئ مشروع Free ثانيًا ثم:
   ```
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file roles.sql --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file data.sql --dbname [CONNECTION_STRING_OF_NEW_PROJECT]
   ```
   ثم تحقق أن `profiles` و`events` ظاهران بصفوفهما.
6. **سؤال مفتوح مهم:** هل تشمل هذه النسخة جدول المستخدمين `auth.users` (بريد وكلمات مرور مجزّأة)؟ **لم أتحقق من ذلك في الوثائق.** إن لم تشمله فالمستخدمون لا يُستعادون ويُعاد تسجيلهم. تحقق في اختبار الاستعادة: افتح `auth.users` في المشروع الثاني. سجّل النتيجة في DECISIONS.
7. المشروع يتوقف بعد أسبوع خمول (مقبول، S-PILOT-4): خذ نسخة قبل أي توقف طويل ثم أعد التشغيل يدويًا من اللوحة.
