## 3. بريد التأكيد (SMTP) — نُفِّذ بـ Brevo (2026-10-15، المالك)

**ما اعتُمد فعليًا (S-PILOT-6):** Brevo (باقة مجانية، 300 رسالة يوميًا بحسب لوحتهم) بمرسل `radlab.pilot@gmail.com`. خطواته كما جرت، لمن يعيدها: (1) تحقق الهاتف في Brevo (شرط منهم قبل مفتاح SMTP؛ تعثر مرات قبل أن ينجح)؛ (2) Senders ← إضافة المرسل (يحذّر Brevo من العناوين المجانية فاختر Add this sender anyway)؛ (3) SMTP & API ← Generate SMTP key؛ (4) **Security ← Authorized IPs ← Deactivate for SMTP keys** (الحجب الافتراضي يمنع عناوين Supabase)؛ (5) في Supabase: Authentication ← Emails ← SMTP Settings: Host `smtp-relay.brevo.com`، Port `587`، **Username = «Login» الظاهر في صفحة SMTP & API (مثل `be…@smtp-brevo.com`) وليس بريد الحساب**، Password = مفتاح SMTP، Sender = بريد المرسل. **جُرِّب بدعوة حقيقية: وصلت إلى Inbox.** يرسل Brevo من نطاق تابع له (`…brevosend.com`) ويجعل `radlab.pilot@gmail.com` عنوان الرد. مفتاح SMTP ينتهي بعد 90 يومًا بلا استخدام. SPF/DKIM/DMARC لم تُفحص بعد (اختياري). **أسلم للتوصيل لاحقًا: نطاق خاص موثّق** (مدفوع، مؤجل).

> النص التالي كان قبل الاعتماد ويُترك للتوثيق: الخادم المدمج لا يصلح…

الخادم المدمج **لا يصلح**: «Send messages only to pre-authorized addresses» (أعضاء مؤسستك فقط)، وحده 2 رسالة في الساعة. المشاركون الخارجيون لن يصلهم بريد التأكيد بدونه.
المطلوب: خدمة إرسال بريد SMTP من اختيارك وإدخال بياناتها في Authentication → SMTP **(قد يختلف)**. لم أقرأ شروط أي خدمة بريد، فاقرأ حدودها المجانية بنفسك أو اطلب جلسة DOCS لمقارنتها. بعد الإدخال جرّب إرسال بريد تأكيد إلى عنوان **ليس عضوًا** في مؤسستك.

2. من checkout نظيف للـcommit المقبول، اعرض أسماء `supabase/migrations/*.sql` بالترتيب المعجمي وخذ `sha256sum supabase/migrations/*.sql` إلى سجل عملية آمن خارج Git يحفظ اسم الملف/البصمة/commit/المشروع/نسخة الأداة/المشغّل/الوقت الحقيقي/النتيجة. **لا تحفظ بيانات اعتماد أو dumps في هذا السجل أو Git.** قاعدة الترتيب: timestamp فريد من14 رقماً ثم اسم، ولا تعديل لملف مطبّق؛ التصحيح ملف لاحق. الاختبار الجديد يكتشف كل ملفات SQL تلقائياً؛ قائمة الخمسة في fixture هي تاريخ اختبار فقط.
3. **مشروع SQL Editor الموجود ليس مشروعاً جديداً:** اجرد الجداول/الأعمدة/defaults/الفهارس/FKs/CHECKs وسياسات RLS والأدوار/الأوامر/predicates، grants الجدول/الأعمدة/sequence/function وSECURITY DEFINER/search_path، والدالة/trigger على auth.users، وقارنها بكل ملف وببصمته من النسخة المقبولة. جرد أسماء فقط أو رسالة Success قديمة لا يثبت التطابق. افحص أيضاً `supabase_migrations.schema_migrations` بـ`supabase migration list` بعد اختيار المشروع الصحيح.
4. إن كان ملف مثبت التطبيق ومطابقاً لكن التاريخ غائباً، يمكن للمالك بعد اعتماد المسار وتصوير الجرد استعمال `supabase migration repair --status applied <timestamp>` للمشروع المحدد. **repair يعدّل ledger فقط ولا ينفّذ SQL**. لا تضع علامة applied لكل الخمسة بالتخمين، ولا تعِد تشغيل أول migration (فيه revoke واسع)، ولا تستخدم IF NOT EXISTS لإخفاء drift. إذا اختلف شيء: توقّف، سجّل الفرق وصمّم migration تصحيح مستقلاً قبل .1؛ لا تصلحه يدوياً خارج السلسلة.
5. في المسار المعتمد لاحقاً: `supabase db push --dry-run` أولاً؛ يجب أن تعرض الخطة الملفات غير المطبقة الصحيحة فقط بالترتيب. راجع الهدف والنسخة والبصمات والنسخة الاحتياطية والاختبار؛ ثم المشغّل الواحد فقط ينفّذ التطبيق. لا تغيّر مشروعاً أو تشغّل push أثناء وجود مشغّل آخر. لا تشغّل `db reset` على مشروع بعيد؛ reset للاختبار المحلي فقط. لا اعتماد على Supabase Branching المدفوع.

#### staging والذرّية والأقفال

- اختبارات CI تبني PGlite جديداً من **كل** الملفات مرتبة، مع محاكاة Auth/roles فقط، وتجرّب ترقية fixture الخمسة؛ ليست خدمة Supabase حقيقية. بعد ذلك يجرّب المالك على **مشروع Free ثانٍ متاح** ببيانات وحسابات اصطناعية فقط (يمكن تناوب staging وتجربة restore على المشروع الثاني). إذا كان المشروع مستخدماً فلا تمسحه أو تستبدله؛ انتظر مشروع تجربة متاحاً. لا تنتقل إلى الإنتاج بمجرد نجاح PGlite.
- للمشروع التجريبي يبدأ المالك من المخطط المعتمد ويطبق الملف السادس **مرة واحدة وفي transaction واحدة**. فهارس CREATE INDEX العادية transactional وتحجز الكتابات أثناء البناء؛ اختبر وقتها وحجمها وتعارض الأقفال أولاً. احتفظ بالفهرسة العادية لهذه الدفعة؛ لا تحوّلها إلى CONCURRENTLY داخل transaction. اختيار CONCURRENTLY لاحقاً يحتاج ملفاً/خطة منفصلة وإدارة فهرس INVALID وغير transactional.
- حدّ انتظار القفل ووقت statement باختيار مُختبر للبيئة (مثال أولي staging: lock_timeout=5s وstatement_timeout=60s، ليست ضمان زمن للإنتاج). إذا استُخدم psql كمسار SQL-editor-compatible، استخدم `--single-transaction --set ON_ERROR_STOP=1 --file supabase/migrations/20261020000100_scale_read_foundation.sql` مع الاتصال الذي يضبطه المالك محلياً؛ لا تُلصق اتصالاً أو كلمة مرور في chat. التشغيل المباشر لا يسجل ledger تلقائياً: بعد النجاح والجرد فقط تُسجل النسخة بما يوافق المسار المعتمد. اختيار CLI لا يعفي من التحقق من حدود transaction للنسخة المثبتة؛ اختبر فشلاً مفتعلاً في staging وتحقق أن فهرساً/default جزئياً لم يبق.
- عند خطأ/مهلة داخل transaction: ألغِها، تحقق من غياب آثار الملف السادس ثم عالج سبب القفل/الخطأ؛ لا تتابع من منتصف الملف. بعد COMMIT لا يوجد rollback تلقائي: أوقف التطبيق التالي، استخدم forward-fix مراجعاً؛ يمكن الإبقاء على الفهارس والـdefault الجديد أثناء التشخيص. إعادة predicates القديمة إن لزم تكون في ملف لاحق من النسخة المرجعية مع جميع شروطها وصلاحياتها؛ لا حذف CHECKs/سياسات أو إيقاف RLS. استعادة dump إجراء استرداد مستقل عند المالك، لا زر رجوع روتيني.
- قبل الإنتاج: نسخة منطقية مشفرة + تجربة restore وفق §8، ثم نافذة القفل والموافقة التشغيلية. تطبيق DB الإضافي قبل أي تطبيق عميل يعتمد عليه؛ هذه الدفعة متوافقة مع العميل الحالي والرموز القصيرة، ولا تحذف توقيع RPC الحالي. في الدفعة .2 احتفظ بالتوقيع القديم حتى خروج النسخ الساكنة القديمة. سجّل pre/post row counts، فهارس valid، predicates/grants/trigger، نجاح حالات العزل، وledger/البصمات والوقت الحقيقي. لا تُسجّل مجرد نجاح push كنجاح للتجربة الحية.

### 8.2. الاستعادة المجربة والتكييفات المحددة

أنشأ المالك مشروع Free منفصلًا في Frankfurt باسم **rad-lab-restore-test**؛ لم يُربط الموقع به. فُحص Session pooler للمشروع الجديد وكونه PostgreSQL17 فارغًا قبل الاستيراد. استُخدم `psql --single-transaction --set ON_ERROR_STOP=1` من الصورة المثبتة، وكلمة مرور من إدخال محلي مؤقت، مع ربط مجلد النسخة بالحاوية **للقراءة فقط**. الأخطاء أوقفت المعاملة ولم تُعتمد المحاولات الفاشلة. لا إعادة استيراد كاملة فوق مشروع الاختبار الذي نجحت استعادته.

1. فشل `roles.sql` عند `GRANT SET ON PARAMETER "log_min_messages" TO "supabase_realtime_admin"`. أكد المالك في المشروع الجديد أن `has_parameter_privilege(...,'SET')=true`. **نسخة العمل `roles.restore.sql` تستبعد هذا المنح وحده**، بعد التحقق من وجوده مرة واحدة؛ لا تغيير صلاحيات مكوّن المنصة أو تعديل الأصل.

ترتيب إعادة التشغيل المخطط من الحزمة (داخل معاملة واحدة وعلى هدف جديد متحقق منه فقط): `roles.restore.sql` → `schema.sql` → `SET session_replication_role=replica` → `data.restore.sql` → `post-restore.sql` → التحقق قبل COMMIT. **إعادة تشغيل الحزمة المجمعة كاملة على هدف فارغ آخر لم تُجرّب**؛ المجرب هو الاستيراد ثم التصحيحات المحددة وملفها المحفوظ والعزل والدخول. لا حذف/إعادة تهيئة للمشروع المجرب لمجرد هذا التوثيق.

**حد snapshot بعد المتابعة الحية:** لاحقًا أظهرت لوحة الموقع الرئيسي محاولتين حديثتين فوق الصف السابق للحساب المختبر (S-PILOT-39.4). الأرشيف هنا التُقط قبلهما ويحتوي محاولة واحدة حسب الجرد أعلاه، ولا يتحدث تلقائيًا؛ لا ندّعي أنه يشمل بيانات ما بعد لحظة النسخ، ولا نختار موعد النسخة التالية ضمن هذا التوثيق.

## 12. إعادة تعيين كلمة المرور — ما يضبطه المالك في لوحة Supabase (RAD-046، لم يُجرَّب حيًّا)

الكود لا يتطلب migration. المطلوب منك ثلاثة أشياء في اللوحة، ثم تجربة واحدة:

1. **Authentication ← URL Configuration:** تأكد أن **Site URL** هو عنوان الموقع الرئيسي، وأن **Redirect URLs** تسمح بصفحة الحساب (`https://<نطاق الموقع>/**` أو `https://<النطاق>/ar/account` و`/en/account`). التسجيل الجديد يستعمل الصفحة نفسها، فغالبًا هي مضبوطة.
2. **Authentication ← Email Templates ← Reset Password:** يجب أن يحتوي القالب على `{{ .ConfirmationURL }}`. القالب الافتراضي إنجليزي؛ يمكنك كتابته بالعربية والإنجليزية معًا (نصان في الرسالة نفسها).
3. **Authentication ← Rate Limits:** سجّل قيمة «emails sent» الحالية. ما هي في مشروعك غير معروف لي؛ إن كانت منخفضة جدًا فقد يفشل طلب رابط ثانٍ بعد أول طلب بدقائق (يظهر للمستخدم «محاولات كثيرة»).
4. **تجربة حية:** من صفحة الحساب اضغط «نسيت كلمة المرور؟» بعنوان حساب تجربة تملكه، افتح الرسالة، اتبع الرابط، اختر كلمة جديدة، ثم سجّل الخروج والدخول بها. صوّر كل خطوة (بدون كلمات مرور ولا روابط الرسالة كاملة، فهي تحوي رمز دخول مؤقتًا).

الرابط في الرسالة يُستعمل مرة واحدة وينتهي سريعًا. إن مرّ الرابط عبر تتبع النقرات في مزود البريد (Brevo) فيجب أن ينتهي إلى صفحة الحساب نفسها؛ إن لم يحدث فسجّل ما رأيت.

**سجل التحقق الحي (2026-10-16، المالك؛ DECISIONS S-PILOT-30):** Site URL وRedirect URLs تغطيان `/ar/account` و`/en/account`؛ قالب Reset Password الافتراضي يحوي `{{ .ConfirmationURL }}`؛ حد البريد 30 رسالة/ساعة للمشروع كله؛ والتجربة بحساب ثانٍ نجحت (بريد، رابط، كلمة جديدة، دخول، خروج). لم يُجرَّب حيًّا: رابط منتهٍ أو مستعمل، وعنوان غير مسجل، وقالب ثنائي اللغة.

### هوية تقييم Practice وصيانتها

`src/features/evaluation/version.ts` يعرّف `radlab-practice-evaluation/1` كأول هوية معلنة لعقد التقييم الحالي؛ ليس رقم حزمة التطبيق أو تاريخ نشر أو إصدارًا منسوبًا لمحاولات سابقة. يسجّل `evaluate` الهوية في WeakMap عند إنتاج النتيجة، ثم يأخذها `buildAttemptRow` من كائن النتيجة الذي يمرره الكاتب الفعلي. لا تتغير النتيجة أو درجاتها أو JSON المحفوظ. النسخ أو النتائج المستعادة دون هذا الدليل تبقى `unknown`؛ والأحداث والملاحظات لا تدّعي أنها نتائج تقييم. إصلاح هوية المحرك وحده لم يحتج ترحيلًا؛ عمود النص الحالي يقبل الهوية. أما هوية مقارنة التعريف المستقلة أدناه فتحتاج عمودًا إضافيًا دون backfill.

عند تغيير معنى نتيجة محفوظة — النتائج الجزئية/الاعتمادات، أوزان التجميع، الإجمالي، النجاح والبوابات الحرجة أو معاني المحاور — يجب رفع هذا الإصدار في التغيير نفسه، مع اختبارات فروق المعنى. تشمل المراجعة `evaluation/engine.ts` و`scoring/score.ts` وتبعيات التقييم: `centering` و`critical` وهندسة الحقل/الماركر وقاعدة الماركر واستجابة المريض ونموذج التقنية. تغييرات العرض والترجمة وحدها لا ترفع هوية المحرك. تغيير قواعد حالة بعينها يُفصل كذلك بهوية المقارنة المستقلة للمحاولات الجديدة وببصمة التعريف للتاريخ الذي لا يحملها؛ خوارزمية `definitionVersion` الأصلية لم تتغير.

الصيانة دلالية يدوية في مراجعة الكود؛ لا اختبار يضمن آليًا أن كل تغيير مستقبلي رفع الإصدار الصحيح، والهوية ليست إثباتًا ضد تزوير عميل. يثبت اختبار `saved-training.test.ts` المسار الفعلي من التقييم والكاتب إلى PostgreSQL/RLS ثم RPC والقارئ وأهلية الرسم، ولا يثبت اتصال Supabase حيًا. هوية النتيجة مؤقتة في الذاكرة حتى الحفظ؛ إن أُضيف لاحقًا عامل خلفي أو استئناف لنتائج محفوظة فسيلزم نقل هوية موثوق معها، وإلا تبقى مجهولة.

اختار المالك في MY-ATTEMPTS-3 **جميع محاولات Practice** كنطاق للمعاينة فقط. البديل حسابات محددة بـUUID محليًا؛ لا تُرسل معرفات الأشخاص في المحادثة. النطاق المرشح محاولات `mode=practice AND record_kind=attempt` الموجودة عند نقطة قطع معتمدة، مع قائمة UUID ثابتة خاصة بالمشغّل. الحسابات والأسماء والأدوار والموافقات لا تُحذف أو تُعدّل. لا يفترض الاختيار عددًا أو توقيتًا أو اعتماد حذف الملاحظات.

قبل كتابة SQL حذف، يشغّل المالك/المسؤول [`practice-reset-inspect.sql`](../supabase/checks/practice-reset-inspect.sql) على المشروع المطابق. الملف قراءة فقط بمعاملة repeatable read ومهلة10 ثوانٍ، وينتهي بـROLLBACK. يُبقي scope=unset افتراضيًا: للمعاينة المختارة يستبدل **الموضعين** بـall-practice محليًا. الصفر مع unset ليس عدًّا للنطاق المختار. يفحص FKs الواردة والصادرة والقيود والمشغلات ودوالها وRLS والمنح والاعتماديات، ثم العدد الكلي وعدد feedback المتتابع والأحداث المرتبطة واختلاف مالك الحدث وتواريخ المدى ومعاينة20 مجموعة دون نصوص أو IDs أو نتائج. إن ظهر ارتباط/مشغّل إضافي أو ملاحظة متتابعة خارج Practice أو انتهاء مهلة، يتوقف إعداد الحذف إلى مراجعته؛ لا رفع تلقائي للمهلة أو توسيع صلاحيات. لا يشمل pg_depend المراجع الديناميكية أو أنظمة خارج القاعدة؛ تُراجع وظائف/مهام الخدمة التي تسجل في هذه الجداول أيضًا.

المعروف من الكود فقط: حذف attempt يحذف feedback المرتبط بـCASCADE؛ أحداث `payload.attempt_id` لا تتبع الحذف. المقترح المحافظ **إبقاء الأحداث** وتوثيق تحول مراجعها إلى تاريخ بلا صف محاولة؛ يُعرض عددها وأثرها في التحليلات قبل الاعتماد. حذف الأحداث إن أراده المالك نطاق إضافي يحتاج اختيارًا وعدًّا ونسخة واعتمادًا منفصلًا، بما فيه منع حذف أحداث المستخدمين الآخرين أو أحداث بلا محاولة. الملاحظات العامة بلا attempt_id تبقى. لا SQL حذف جاهز قبل نتائج catalogue الحي، ولا عدّ أو نسخة حية منفذة من الوكيل.

**نسخة قابلة للاسترجاع، ينفذها المسؤول خارج المستودع:** بعد نافذة منع الكتابة وقبل أي حذف، يجهّز مساحة محلية خاصة ومشفرة وصلاحيات0700، وملف خدمة PostgreSQL وpgpass محليين بلا أسرار في الأوامر أو Git. بأدوات PostgreSQL المتوافقة مع الخادم، مثال توجيهي للنسخة الكاملة للجداول الثلاثة: `pg_dump --dbname=service=radlab-pilot --format=custom --data-only --table=public.attempts --table=public.feedback --table=public.events --file=/secure/radlab/practice-before-reset.dump`. تحتوي النسخة بيانات أشخاص: المكان مشفر فعليًا قبل التشغيل، ولا تُرفع أو تُشارك أو تُترك في workspace. يحتفظ محليًا ببصمة SHA-256 ووقت القطع ونسخة schema/الترحيلات وmanifest خاص بمعرفات المرشحين، وعدد كل جدول وعدد المرشحين ونتائج تحقق التطابق. لا تكفي نسخة CSV الملخصة لاستعادة settings/result أو feedback. لا تُسمّى هذه الخطة «نسخة موجودة»؛ نجاح pg_dump وسلامة الملف وإمكانية فك تشفيره وتجربة الاستعادة شروط لازمة.

**تجربة الاستعادة:** يفحص `pg_restore --list`، ثم يستعيد نسخة الجداول كاملة داخل قاعدة معزولة خاصة من المخطط المطابق، مع تبعيات auth.users/profiles/locale وroles مهيأة من نسخة محمية أو استنساخ معتمد للبيئة نفسها. لا يكفي مخطط فارغ لإرضاء FKs، ولا تُعطل القيود لتجاوز نقص التبعيات. يستعمل `pg_restore --exit-on-error --data-only` ويقارن كل الأعمدة والـUUIDs والعدد وJSON/timestamps والروابط بالmanifest والنسخة. لا اتصال أو رسائل أو نشر من قاعدة التجربة. يسجّل نجاح التجربة منقحًا فقط في RAD-058. يضمن بقاء النسخة ومفتاحها لدى المسؤول ضمن مدة الاحتفاظ المعتمدة.

**إجراء الاستعادة بعد تنظيف معتمد:** إعادة منع الكتابة أولًا؛ استعادة الملف في staging خاصة معزولة، ثم تجهيز معاملة تعيد فقط قائمة المحاولات المحذوفة بأعمدتها الأصلية، ثم feedback المرتبط بأرقام صفوفه ووقته، والتحقق من كل قيمة وقيد قبل COMMIT. أي تعارض UUID/رقم feedback يوقف الاستعادة للمراجعة؛ لا ON CONFLICT يتجاهل اختلافًا ولا TRUNCATE أو استبدال جداول الإنتاج. الأحداث المحتفظ بها لا تُستورد ثانية. يراجع المسؤول sequence الملاحظات بعد استعادة الأرقام ويحافظ على عدم التراجع تحت أكبر رقم قائم. هذه استعادة إنتاج مستقلة تحتاج إذنًا محددًا؛ لا تُشغّل pg_restore الكامل مباشرة على الإنتاج. بعد استعادة قاعدة أو تغيير SQL/المنح يعاد إجراء إثبات الجاهزية ومسار الخدمة قبل النشر.

**منع السباق والكاتب القديم:** نجاح نشر المسودة لا يحدّث main أو الروابط القديمة أو التبويبات المفتوحة. يجرد المالك النسخ المستخدمة ووجهات رفعها؛ لا يُنشر main أو تُلغى روابط أو تتغير سياسات تلقائيًا. قبل نافذة التنظيف، يحدد وسيلة إيقاف كتابة فعلية لجميع المصادر، لا لافتة واجهة فقط: مثل حجب إدخالات attempts/feedback/events مؤقتًا على الخادم بأذونات إدارية محددة ومعروفة الأثر، مع اختبار رفض عميل قديم. اختيار الوسيلة وتطبيقها واسترجاعها يحتاجان إذن إنتاج محددًا منفصلًا؛ لا ينفذه هذا الإجراء. بعد تفعيل المنع تُنتظر الطلبات الجارية وتُراجع الكتابة المتأخرة وتُعاد الأعداد والنسخة عند نقطة القطع. عند تنفيذ حذف لاحقًا داخل معاملة قصيرة، تُقفل الجداول/العلاقات ذات الصلة بمهلة محدودة ويُتحقق من العدد والmanifest من جديد؛ يمنع الإيقاف إعادة كتابات كانت تنتظر القفل بعد COMMIT. لا نفتح الكتابة حتى تثبت وجهة الكاتب المصحح وتتعذر كتابة النسخ القديمة؛ وإلا يؤجل التنظيف بدل الادعاء بمنع unknown. سياسة رفض unknown/الهوية الفارغة على الخادم تغيير مستقل، لا تُطبق ضمن هذا الطلب.

بعد تحقق catalogue والعدد والمعاينة والنسخة وتجربة الاستعادة وخطة الإيقاف الفعلية، يعرض للموافقة النهائية: المشروع، scope ونقطة القطع، عدد المحاولات وfeedback، إبقاء الأحداث وعددها، معرف النسخة المحلي المنقح ودليل استعادتها، وسيلة المنع ونافذته وخطة الرجوع. عندها فقط يُجهّز ويُعتمد SQL الحذف المحدد. إذا تغير العدد أو النطاق أو المخطط لا تنفذ موافقة قديمة. بعد اعتماد وتنفيذ فعليين يختبر المالك محاولتين جديدتين للحالة نفسها ويسجل درجتيهما الفعليتين وتطابق الحفظ والرسم وفحص الهاتف؛ لا اختلاق درجات. التنظيف ليس إصلاح الرسم ولا شرط حفظ التاريخ مستقبلًا.


<a id="training-deployment-check"></a>
### التدريب: التحقق قبل نشر رابط المراجعة

بعد بلاغ المالك عن فشل الملف الشخصي في حسابين، أُعيد إنتاج السبب محليًا: الواجهة الجديدة تطلب `display_name`، والقاعدة ذات الترحيلات الثمانية ترفضه بـ42703. اختبارات النسخة الأولى كانت تهيّئ القاعدة كاملة أو تعيد بيانات اصطناعية، فلا تثبت توافق مشروع المعاينة. الصورة وحدها لا تؤكد رمز الخطأ الحي؛ هذا المسار يمنع نشر واجهة جديدة دون تسجيل تحقق التوافق، ولا يغيّر قواعد حية تلقائيًا.

1. **حدّد المشروع المقصود:** طابق مشروع Supabase مع `NEXT_PUBLIC_SUPABASE_URL` المستخدم في بناء Pages. لا تفترض أن للمعاينة قاعدة منفصلة عن الإنتاج؛ إذا كانت مشتركة فذلك تغيير إنتاج يحتاج إذنًا منفصلًا. لا ترسل مفاتيح أو بيانات حسابات في المحادثة.
2. **تحقق دون كتابة:** نفّذ [`supabase/checks/training-ready.sql`](../supabase/checks/training-ready.sql) من محرر SQL في المشروع المقصود. يعمل داخل معاملة read only تنتهي بـrollback، ويتحقق من العمود والدوال والفهرس والمشغّل وRLS والمنح. `TRAINING_SCHEMA_NOT_READY` يعني التوقف، وليس توسيع المنح يدويًا. عند فشل الفحص نفّذ `ROLLBACK;` لإنهاء المعاملة قبل أي خطوة تالية. لا تشغّل SQL باستبدال رسالة الخطأ أو تجاهلها.
3. **إذا كان التحديث ناقصًا:** راجع سجل الترحيلات. الترحيل الإضافي المطلوب هو [`20261020000400_training_dashboard.sql`](../supabase/migrations/20261020000400_training_dashboard.sql)، بعد سابقاته؛ لا تعِد تشغيل ترحيل مطبّق. إضافة العمود وحده غير كافية. تطبيقه على البيئة المقصودة يحتاج الإذن المناسب؛ لم يُطبّق على مزوّد في هذه الدفعة. أعد الفحص بعد التطبيق المصرّح به. إذا كانت الحالة جزئية فلا تعِد SQL كاملًا عميانيًا؛ راجع التغيير الجزئي أولًا.
4. **تحقق من مسار الخدمة:** نجاح SQL يفحص catalogue والمنح، ولا يثبت Auth أو مخبأ PostgREST أو سلوك RLS الحي. في البيئة المصرّح بها، تحقّق من قراءة الملف الشخصي عبر الخدمة بحساب مشارك وحساب مالك، ونجاح RPC التدريب في نطاقهما، ورفض اختيار مستخدم آخر للمشارك. يمكن استخدام بناء محلي متصل بالبيئة المصرّح بها؛ لا يحتاج هذا نشر رابط معطّل أولًا. احتفظ بالنتيجة المنقّحة دون رموز جلسة أو بيانات أشخاص في دليل RAD-058.
5. **سجّل إثبات التوافق بعد نجاح الخطوتين السابقتين فقط:** يحدد [عقد الواجهة](../scripts/pages/frontend-schema.json) الترحيلات والفحوص المطلوبة؛ الخلفية المؤجلة ليست إذنًا لتطبيقها، وتغيير التصنيف أو مصدر اتصال يحتاج مراجعة الكود. في نسخة المستودع التي ستُنشر، شغّل `node scripts/pages/pilot-schema-gate.mjs --print-marker` مع متغير البيئة العام `NEXT_PUBLIC_SUPABASE_URL` للمشروع المقصود. لا يحتاج الأمر كلمة مرور أو مفتاحًا سريًا ولا يتصل بالقاعدة. انسخ الناتج `pilot-v1:…` إلى GitHub Repository Actions Variable باسم `PILOT_SCHEMA_VERIFIED`. لا تضعه في متغير `NEXT_PUBLIC_*`، ولا تسجّله قبل التحقق أو بهدف تجاوز فشل النشر.
6. أعد تشغيل workflow النشر للتغيير المقصود، ثم افحص الهاتف الفعلي. عند غياب الإثبات أو اختلاف المشروع أو بصمة ملفات الترحيلات/فحص SQL، يتوقف الـworkflow **قبل البناء والرفع** ويستبدل تعليق الرابط برسالة حجب، دون نشر رابط جديد. تعطيل الحسابات بغياب متغيرَي Supabase معًا لا يتطلب إثباتًا؛ الإعداد الجزئي غير مقبول للنشر.

في MY-ATTEMPTS-3 يلزم أيضًا تشغيل [`comparison-ready.sql`](../supabase/checks/comparison-ready.sql) بعد فحص التدريب الأصلي؛ فحص التدريب يبقى بعقده السابق، والحارس يربط الفحصين مع سلسلة الترحيلات. نجاح التدريب وحده لا يكفي للعميل الجديد.

هذا إثبات يدوي مرتبط بالمشروع وبمحتويات SQL، وليس استعلام صحة حيًا من الـworkflow. إذا تغيّر المخطط خارج Git أو استُعيدت القاعدة أو تغيّرت المنح/المشروع، يُمسح المتغير ويُعاد التحقق قبل تشغيل النشر؛ لا تستطيع البصمة كشف الانحراف الحي وحدها. إعادة التحقق تلقائيًا تتطلب مستقبلًا اتصال CI معتمدًا للقراءة فقط، ولم يُضف هنا أي سر أو اتصال أو إعداد مزوّد. الحارس يغطي workflow `deploy-pages.yml`؛ الرفع اليدوي أو Git integration يحتاجان هذا الإجراء أيضًا ولا يمران بالحارس تلقائيًا. الروابط القديمة لا تتحدّث بهذا التغيير ولا تُعدّ دليل جاهزية.

رسائل الواجهة تصنّف رمز الخطأ وتمنع تخمين ملف أو صلاحية عند غياب المخطط؛ تميّز التحديث المطلوب عن الشبكة والجلسة والصلاحيات والملف المفقود. اختبار المتصفح [`pilot-schema-audit.mjs`](../scripts/qa/pilot-schema-audit.mjs) يشغّل الواجهة الحالية مقابل PostgreSQL محلي حقيقي بمخطط قديم وجزئي ومحدّث، عبر موائم طلبات بشكل PostgREST، مع Auth وأحداث اصطناعية. هذا يغطي التعارض الذي فات الفحص الأول، ولا يُسمّى تحققًا من مزوّد حي.

<a id="training-owner-service-check"></a>
### تنفيذ المالك لفحص الخدمة دون مشاركة أسرار

عندما لا تسمح شبكة بيئة الوكيل بالمشروع أو لا توجد جلسات مهيأة، ينفّذ المالك [`scripts/pilot/live-service-check.js`](../scripts/pilot/live-service-check.js) من Console في متصفح حاسوب على الموقع الذي يستعمله بالفعل. لا حاجة إلى فتح الوكيل معاينة مستضافة أو نشر نسخة جديدة قبل الفحص. الإجراء موجّه حصريًا إلى مشروع `vlacestfruxooznrcjqc` الذي طُوبق مع سجل النشر؛ لا يُعاد استعماله لمشروع آخر دون مراجعة وربط جديدين. هو أداة تشغيل يدوية لا جزء من حزمة التطبيق، ولا ينشئ حسابًا أو محاولة أو حدثًا ولا يغيّر متغير النشر. الـPOST الوحيد هو RPC القراءة المستقرة `training_page_v1`؛ جميع القراءات المحدودة تطلب عنصرًا واحدًا، ولا تُتبع صفحات. تجميع الملخص يستخدم دالة الخدمة الحالية.

1. جهّز حساب المالك وحساب مشارك مختلفًا، وكلاهما approved. من Supabase → Authentication → Users، انسخ UUID كل حساب إلى مكان خاص على جهازك لتدخله في الفحص المقابل. لا ترسل UUID أو البريد أو مفاتيح أو جلسات في المحادثة. استخدم فقط مفتاح المشروع العام الذي يبدأ بـ`sb_publishable_` من إعدادات API؛ لا تستخدم `sb_secret_` أو service_role. نجاح SQL السابق محفوظ؛ لا تعِد تشغيل ترحيل التدريب.
2. افتح الموقع الموجود وسجّل الدخول بحساب المالك. افتح أدوات المطوّر (F12 أو قائمة المتصفح → أدوات المطوّر)، ثم Console. راجع الملف المرتبط أعلاه، والصق محتواه كاملًا وشغّله مرة واحدة. لا تلصقه في SQL Editor. عند طلب المفتاح أدخل publishable العام محليًا؛ وعند طلب الحساب الآخر أدخل UUID المشارك. يقرأ الإجراء رمز الجلسة الحالية داخليًا ويرسله إلى المشروع المحدد فقط، دون طباعته أو طلبه منك.
3. انسخ فقط السطر الذي يبدأ بـ`RADLAB_SERVICE_CHECK`، أو صوّره وحده. نتيجة المالك يجب أن تحمل `outcome: PASS` و`role: owner`. يتحقق الإجراء من Auth والملف الشخصي والتدريب الشخصي ونطاق المالك وقراءة المشارك المحدد، ومن وجود ذلك المشارك واعتماده فعليًا. لا يطبع الأسماء أو البريد أو UUID أو الدرجات.
4. سجّل الخروج، أو استخدم ملف متصفح منفصلًا، ثم سجّل الدخول بحساب المشارك وشغّل الملف نفسه. أدخل المفتاح العام نفسه وUUID المالك هذه المرة. يلزم `outcome: PASS` و`role: participant`، بعد نجاح الطلب الشخصي ورفض RPC لبيانات الآخر ولنطاق all برمز403/42501، وإخفاء صف الملف والمحاولات للآخر. فشل/انتهاء الجلسة وحده لا يمرر فحص الرفض.
5. أرسل السطرين المنقّحين فقط. يجب تطابق `pair` فيهما، وهو بصمة للزوج والمشروع دون نشر معرفَي الحسابين. يربط ذلك حساب المشارك الذي تأكد المالك من وجوده بحساب المالك المستخدم في التشغيل المقابل. `STOP` يعني التوقف وإرسال هذا السطر المنقّح للتشخيص؛ لا ترسل بقية Console أو Network أو localStorage أو ردود الخادم. في مرحلة setup: الرمز `OTHER_ACCOUNT_UUID_INVALID` يعني أن المدخل ليس UUID كاملًا بصيغة8-4-4-4-12؛ و`OTHER_ACCOUNT_MATCHES_CURRENT_SESSION` يعني أنه الحساب المسجّل نفسه؛ و`OTHER_ACCOUNT_INPUT_CANCELLED` يعني إغلاق نافذة المدخل. لا طلب خدمة عند هذه الأخطاء، ولا تخمّن قيمة بديلة. إن احتجت تصحيح المدخل أو إعادة الدخول فأعد المحاولة يدويًا؛ الأداة لا تجدد الرموز أو تعيد الطلبات تلقائيًا.
