## Backup preparation and RLS boundary

[The scoped SELECT/policy approval](DECISIONS.md#assess-self-service-s4-backup-owner-2026-11-06) authorises offline preparation only. The compiler `scripts/ops/prepare-cloud-backup.mjs --inventory /outside/catalogue.json --output /outside/new-directory` accepts bounded nonsecret metadata and emits an exact dry-run grant packet. The committed inventory measures the pinned no-data production schema plus S1–S4 and W1/v2 binding: 119 relations, 11 schemas, five extensions. It is a synthetic candidate, never a substitute for provider inventory. `supabase/checks/selfservice-backup-inventory.sql` is the bounded owner READ ONLY packet; no live execution here. It returns ownership/grant gaps and PUBLIC constructor capabilities without rows, function bodies, settings values, passwords or Vault plaintext. No missing provider object may be excluded to match this pin.
The packet creates only a closed, noninheriting assess_backup role, exact SELECT on the enumerated tables/sequences/LOBs, necessary schema USAGE/DB CONNECT and additive permissive SELECT true policies solely for that role. Existing policy rows remain byte-exact. No table/schema/function ownership, write/admin/default grant, membership, BYPASSRLS, LOGIN/password or decrypt permission. Existing restrictive policies, role drift, uncovered provider ownership, extra effective write/SECDEF/decrypt privilege or inventory drift refuse and roll back. Provider-owned policy installation and membership-free role creation require already-held authority: unsupported managed ownership is STOP, not a reason to grant extra roles.
The actual command is `pg_dump --format=custom --create --enable-row-security --lock-wait-timeout=5s --snapshot=...`; the runner proves full-row policy/SELECT access before using RLS export. It rejects unpinned objects, filtered extension configuration, foreign/materialized required data and missing native TABLE DATA/LOB entries. Every required table is counted under the exported repeatable-read snapshot; ACCESS SHARE permits concurrent DML while blocking conflicting relation DDL. All LOB bytes use the same snapshot. Native archive sequence positions are non-MVCC: only ascending noncycling sequences are supported, archived values must not rewind initial high-water or the owned-column snapshot maximum. A reset violation is STOP without upload or repair; positions may be newer than table rows and may leave gaps. Native role SQL is restored inside a private socket-only memory cluster and compared to snapshot role metadata; role drift/membership/settings mismatch is STOP. Fresh catalogue/inventory fences after native exports reject schema/type/enum/default-ACL/event-trigger and role changes; physical catalogue maintenance can conservatively STOP. No blind retry or claim of a single global snapshot for sequences/roles.
The job defaults to zero connections/uploads. `--run` reads one exact numeric Secret Manager binding, fixed direct host/assess_backup and verified TLS; scratch is non-root uid999 memory only. Password files/CA and plaintext archives are ephemeral and cleaned in finally. Only the public age recipient enters the job; private identity stays on the restore owner's host. Password-free role SQL, database archive including database settings/ACL, metadata and checksums are tarred then age-encrypted before unique-name/generation-match0 upload. The output separates `coverage=all-pinned-database-objects` from `providerRecoveryVerified=false`; it never attests full platform recovery.
Native tests prove actual commands, fresh restore, negative table/sequence/RPC/SET ROLE privileges, concurrent DML/LOB changes, advancing/reset sequences, queued DDL, schema ABA, enum changes and role-archive ABA. Required CI additionally builds the unchanged pinned image on supported Ubuntu24.04 (ubuntu-latest moved to26.04 and lacks the required PG16 packages), checks default/network-none/non-root/memory scratch/TLS, provider-owned Auth/Storage/Vault ciphertext/partition rows, roles, native restore and upload failure/cleanup. Image verification is pending the final pushed-head proof; no assertion or base is relaxed for local vfs capacity.
**Remaining provider limits:** actual inventory/ownership/plan and native provider dump/restore are Not run (no live authority). Provider configuration, extension binaries, global authentication passwords, secret stores and external encryption/recovery material require a separate owner-held recovery inventory. Passwords are deliberately excluded and must rotate after restore. ### Additional PUBLIC large-object privilege boundary (2026-11-06)
Verified on isolated PostgreSQL17.11: assess_backup can execute `pg_catalog.lo_create(oid)`, `lo_creat(integer)` and `lo_from_bytea(oid,bytea)` through default PUBLIC EXECUTE; all three actually create a large object despite zero table/sequence writes, CREATE/TEMP, memberships or BYPASSRLS. SELECT/RLS alone cannot deny inherited PUBLIC privileges. A read-only transaction protects this job, but cannot make a stolen credential unable to call these functions in another transaction.
Concrete proposal, **not approved/applied**: pin these three exact existing function ACLs plus the existing role-name set; atomically preserve each existing role's effective EXECUTE by exact named grants, then revoke only PUBLIC EXECUTE on the three constructors. Exclude only the new assess_backup role; no memberships, grant options, admin grants, function replacement or default grants. Require existing ownership/authority, CLOSED/NOLOGIN/zero backup backends and exact before/after ACL checks; refuse unsupported managed-provider ownership. Existing roles retain access; future roles no longer inherit these three operations automatically and need explicit review. Rollback stays NOLOGIN and paused; no automatic PUBLIC regrant. This is an additional protected privilege exception, outside the approved SELECT/policy packet. Until decided/proved, strict no-write backup readiness is STOP and laptop backup remains required.
The current bounded owner inventory is read-only; no actual provider SQL was run. The final image proof and remaining independent backup work continue without changing PUBLIC permissions.
