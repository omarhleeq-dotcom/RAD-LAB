# تنسيق ملف الحالة وقواعد تحديثه

الملف: [`project-status.md`](project-status.md) (مصدر وحيد للحالة الحالية، يحدّثه Claude Code وCodex ويُعرض لاحقاً في Obsidian). هذا المستند يصف تنسيقه فقط؛ لا يغيّر أي قرار في `DECISIONS.md`.

## 1. بنية الملف

1. **ملخص عربي** (سرد، لا يُقرأ آلياً).
2. **كتلة البيانات الحالية**: كتلة JSON واحدة محصورة بين العلامتين التاليتين، وهي الجزء الوحيد المقروء آلياً:

   ````
   <!-- STATUS-DATA:BEGIN -->
   ```json
   { ... }
   ```
   <!-- STATUS-DATA:END -->
   ````
3. **سرد تاريخي**: جدول مختصر منفصل عن البيانات. التاريخ ليس مهاماً؛ قرار قديم لا يُحوَّل إلى مهمة مفتوحة.

## 2. حقول المستوى الأعلى (كلها مطلوبة)

| الحقل | المعنى |
|---|---|
| `project` | اسم المشروع (`RAD-LAB`) |
| `format_version` | إصدار تنسيق الملف (`"1.0"`)؛ يتغيّر فقط عند تغيير هذا المستند |
| `revision` | عدد صحيح ≥ 1، **يزيد بواحد عند أي تغيير في الحالة** (مهمة جديدة، حالة، عنوان، وصف، دليل)؛ ويفرض الفحص زيادته (أي مقدار) مع تحديث `updated_at` عند تغيّر المهام أو `next_id` |
| `updated_at` | وقت التحديث ISO 8601 مع إزاحة (`2026-10-13T02:40:00Z` أو `+03:00`) |
| `timezone` | اسم المنطقة الزمنية للقيمة السابقة (`UTC` أو IANA) |
| `next_id` | المعرّف التالي غير المستخدم (`RAD-027`). كل معرّف قائم أصغر منه، فلا يُعاد استخدام معرّف |
| `tasks` | مصفوفة المهام |

## 3. حقول المهمة

| الحقل | مطلوب | الوصف |
|---|---|---|
| `id` | نعم | `RAD-NNN`، ثابت لا يتغيّر ولا يُعاد استخدامه |
| `title` | نعم | عنوان واضح |
| `status` | نعم | `planned` · `in_progress` · `review` · `blocked` · `deferred` · `done` |
| `priority` | نعم | `high` · `medium` · `low` |
| `description` | نعم | المطلوب أو **المتبقي فعلياً** (لا تاريخ العمل) |
| `source_ref` | نعم | تقرير/قرار/ملف يثبت الحالة (مثل `DECISIONS.md S14.5-9`، `docs/session-14.5-ankle.md`) |
| `completion_evidence` | عند `done` فقط | دليل الإنجاز المناسب لطبيعة المهمة |
| `blocker` | عند `blocked` | ما يمنع التقدّم ومن يملك رفعه |
| `defer_reason` | عند `deferred` | لماذا أُجّلت ومن قرّر |
| `conflict` | اختياري | وصف تعارض بين مصادر، مع المصدر المعتمد وسبب اعتماده |

لا حقول أخرى. كل مهمة تظهر **مرة واحدة** فقط في البيانات الحالية؛ الإشارات المتبادلة تكون بالمعرّف داخل النص.

### معنى الحالات

- `planned`: معروفة ومقرّرة ولم يبدأ العمل. **المخطط لا يُسجَّل كأنه منفّذ.**
- `in_progress`: يجري العمل فعلاً (دفعة تغييرات مفتوحة).
- `review`: ينتظر قراراً أو مراجعة بشرية، أو فيه تعارض مصادر لم يُحسم. لا تُخترع حالة مؤكدة.
- `blocked`: لا يمكن التقدّم بسبب مذكور في `blocker`.
- `deferred`: مؤجَّلة بقرار موثّق في `defer_reason`.
- `done`: منجزة **ومعها دليل تحقق** (انظر §5).

## 4. قواعد التحديث (لكل الجلسات)

1. اقرأ آخر نسخة من الملف قبل البدء.
2. عند انتهاء الجلسة حدّث **المهام التي تغيّرت فعلياً فقط**، وزِد `revision` وحدّث `updated_at`.
3. لا تسجّل العمل المخطط كأنه منفّذ؛ ولا تستنتج الإنجاز من عنوان جلسة أو وجود ملف.
4. لا تستخدم `done` دون دليل تحقق مناسب لطبيعة المهمة (§5).
5. حافظ على المعرّفات والملاحظات والأقسام التي لا تخص تحديثك. لا تحذف مهمة؛ غيّر حالتها أو أضف ملاحظة. مهمة جديدة تأخذ `next_id` ثم يُزاد `next_id`.
6. اجعل تحديث الحالة ضمن **نفس دفعة تغييرات العمل** (نفس الـcommit أو الـPR).
7. قبل الدمج راجع أحدث نسخة من الفرع المستهدف وحُلّ التعارضات **دمجاً** دون استبدال تحديثات الآخرين (يتعارض عادةً `revision` و`updated_at` و`next_id`: خذ الأعلى وأعد الحساب). إذا استُخدم المعرّف نفسه لمهمتين مختلفتين على فرعين، أعطِ المهمة الأحدث `next_id` وسجّل ذلك.
8. إذا تعذّر تحديث الحالة فاذكر السبب في التقرير النهائي.
9. عند تعارض المصادر: اكتب التعارض في `conflict`، اعتمد المصدر الأعلى حسب قاعدة المشروع (`DECISIONS.md` ثم `exam-recipe.md` ثم ROADMAP)، وضع `status: review` إن كان الحسم يحتاج المالك. لا تحسم بالتخمين.
10. قرار تاريخي مغلق (مثل O1) ليس مهمة مفتوحة. بنود O المفتوحة تُجمَّع في مهمة واحدة بحسب الجهة المسؤولة بدل نسخ كل بند كمهمة.

## 5. ما يكفي كدليل لـ `done`

| طبيعة المهمة | دليل مناسب |
|---|---|
| كود/بيانات | PR أو commit مدموج + اختبارات تغطي التغيير + نتيجة `npm run check` (وبناء `npm run build` عند الحاجة) |
| فحص جديد | ما سبق + حارس scene-dom الخاص به + تدقيق المتصفح EN/AR عند اشتراط الوصفة |
| توثيق فقط | الملف مدموج في الفرع المستهدف + مرجع القرار؛ وهذا **لا يثبت صحة المحتوى الطبي** |
| قرار المالك | سجل القرار في `DECISIONS.md` بتاريخه |
| تحقق خارجي (رخصة، نشر) | رابط/لقطة/تاريخ التحقق؛ وإلا فلا `done` |

## 6. الفحص الآلي

### 6.1 الفحص البنيوي (دائماً)

```
npm run status:check          # يطبع المشاكل ويخرج برمز 1 عند وجودها
npm test                      # يشغّل src/features/qa/project-status.test.ts ضمن الاختبارات (وبالتالي CI)
```

يتحقق من:

- **كتلة بيانات واحدة**: علامة `STATUS-DATA:BEGIN` واحدة وعلامة `STATUS-DATA:END` واحدة بالترتيب الصحيح، وبينهما كتلة ` ```json ` واحدة فقط؛ يُسمح بالمسافات والأسطر الفارغة حولها، ويُرفض أي نص آخر أو كتلة ثانية داخل القسم. الملخص والسرد التاريخي خارج العلامتين مسموحان (لا يُقرآن آلياً).
- JSON صالح، الحقول المطلوبة ومنع الحقول الغريبة، صيغة المعرّف وعدم تكراره، `next_id` أكبر من كل المعرّفات، الحالات والأولويات المسموحة، `revision` ≥ 1 ووقت ISO بإزاحة، وجود `completion_evidence` للمنجز و`defer_reason` للمؤجل و`blocker` للمتعطل، ومنع `completion_evidence` في غير المنجز.

### 6.2 فحص الانتقال مقابل النسخة السابقة

`next_id` وحده لا يثبت أن معرّفاً لم يُعَد استخدامه، لذلك يقارن الفحص الحالة الجديدة بالسابقة:

| القاعدة | الخطأ عند المخالفة |
|---|---|
| لا يُحذف معرّف مهمة كان موجوداً | `task deleted` |
| لا يتراجع `next_id` ولا `revision` ولا `updated_at` | `... went back` |
| المهمة الجديدة تأخذ رقماً ≥ `next_id` السابق | `below the previous next_id` |
| تغيّر أي مهمة أو إضافة/حذفها أو تغيّر `next_id` ⇒ `revision` أكبر **و** `updated_at` أحدث (زمنياً) | `revision was not increased` / `updated_at was not updated` |
| دون تغيير في المهام و`next_id` يجوز بقاء `revision` و`updated_at` كما هما | ـ |

تغيّر عنوان المهمة (أو أي حقل نصي) وحده **ليس** إعادة استخدام للمعرّف؛ هو تغيير بيانات يستلزم فقط رفع `revision` وتحديث الوقت. المقارنة بالمعرّف، لا بالترتيب.

**التشغيل محلياً** (من جذر المستودع، والفرع الحالي فيه الملف الجديد):

```
npm run status:check -- --base origin/main            # النسخة عند نقطة التفرّع (git merge-base origin/main HEAD)
npm run status:check -- --previous /path/old-status.md   # أو مقارنة بملف سابق مباشرة
npm run status:check -- --base origin/main --require-previous   # يفشل إن لم يوجد ملف سابق
```

(نفّذ `git fetch origin main` أولاً ليكون `origin/main` محدّثاً.) بلا `--base` ولا `--previous` يُجرى الفحص البنيوي فقط ويطبع الأمر ذلك صراحةً.

**في CI (على PR فقط):** يستخدم `.github/workflows/ci.yml` الخيار `--base origin/<الفرع المستهدف> --head <head.sha للـPR>` مع `fetch-depth: 0`. يمرّر `--head` لأن CI يختبر الـ merge commit، فـ`merge-base` مع `HEAD` كان سيعطي رأس الفرع المستهدف لا نقطة التفرّع الحقيقية.

**التهيئة الأولى:** حين لا يوجد ملف حالة عند نقطة التفرّع (كأول PR يُضيفه) يُكتفى بالفحص البنيوي ويُطبع ذلك صراحةً (`initial setup, structure only`). بعد وجود الملف على الفرع المستهدف تبدأ المقارنة تلقائياً.

**لا يُتجاوز أي خطأ بصمت:** تعذّر تحديد نقطة التفرّع (مرجع غير موجود، clone سطحي)، أو تعذّر قراءة الملف السابق، أو نسخة سابقة غير قابلة للقراءة، كلها أخطاء تُفشل الفحص.

### 6.3 حدود الفحص

- هو فحص **تنظيمي واستمرارية معرّفات**؛ **لا يثبت صحة وصف المهمة ولا دليل إنجازها** (`completion_evidence` يُفحص وجوده فقط). مراجعة الدليل مسؤولية من يحدّث الملف ومن يراجعه.
- من يحذف الملف نفسه أو ينقله أو يعيد إنشاءه عند فرع لا يوجد فيه ملف سابق يُعامَل كتهيئة أولى. لذا بعد دمج PR الأول يُستحسن إضافة `--require-previous` إلى خطوة CI (غير مفعّل الآن حتى لا يفشل PR التهيئة نفسه).
- يقارن بنسخة نقطة التفرّع، لا بآخر تحديثات الفرع المستهدف؛ تعارضات الدمج مع جلسات أخرى تُحل يدوياً حسب §4 (بند 7).
- يعمل على مسار الملف الافتراضي؛ نقل الملف أو تغيير اسمه يلزمه تحديث الأمر في CI.

## 7. ملاحظة لعرض Obsidian (لاحقاً)

الملف Markdown عادي، وكتلة JSON محددة بعلامتين ثابتتين ليستطيع أي أداة لاحقة قراءتها دون تحليل النص العربي. لم يُبنَ أي مراقب أو ربط في هذه الجلسة.
