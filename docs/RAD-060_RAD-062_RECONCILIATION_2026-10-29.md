# RAD-060 وRAD-062 — مصالحة قراءة فقط وخطة للموافقة، 2026-10-29

## 1. الانحرافات والميزانية

الهدف: تحديد المنفذ والمتبقي والخامل، ثم اقتراح أصغر دفعة آمنة. أمر المالك الحالي يستأنف **التخطيط فقط**؛ التنفيذ ينتظر موافقته على الخطة. الميزانية ثلاثة ملفات توثيق: هذا التقرير، [project-status](project-status.md)، و[HANDOFF](HANDOFF.md). صفر وحدات منتج مشتركة؛ لا كود أو SQL أو migration أو UI أو إعدادات أو اتصال بقاعدة حية. لا انحراف عن الميزانية، ولا worktree أو subagents.

بدأت بـAGENTS وdocs:context وstatus:summary وقراءة أدلة المهمتين والقرارات وخطة Assess وأدلة التجربة وRAD-085. بعد fetch تطابق HEAD مع origin/main عند `45d650b`؛ أداة GitHub المتصلة أثبتت دمج [#155](https://github.com/omarhleeq-dotcom/RAD-LAB/pull/155). هذا يثبت قاعدة القراءة، ولا يثبت نشر ذلك الرأس. أدلة الحي هنا **إفادات المالك المحفوظة**، وليست قياسًا جديدًا من الوكيل. نسبة DB نحو3% وصفوف التأليف0 من سياق المالك الحالي؛ لا تحويل لهما إلى شاهد SQL جديد.

## 2. المنجز والمستبعد

النتيجة: وصف RAD-060 «SQL محلي جزئي وزر باقٍ» متقادم؛ الدوال مطبقة حيًا، والزر والتأكيد موجودان في مكوّن P2 محلي، لكنهما غير موصولين بالموقع. وصف RAD-062 «لا برمجة قبل الاستئناف/المشرف من الصفر/RAD-060 مع أول migration» لم يعد يصف الأساس الحالي: P1 موجود ومجرب هاتفيًا، وبنية P2 مطبقة وخاملة، والبرمجة الجديدة تحتاج موافقة الخطة الحالية.

صُححت المهمتان فقط، مع إحالة إلى هذا التقرير وحفظ مصادرهما السابقة؛ كلاهما review/waiting_on owner للموافقة، وليستا done. RAD-062 تنتقل من planned إلى review لأن خطة المصالحة أصبحت معروضة، لا لأن الكتابي أو الصور نُفذا. أُعيدت كتابة ملخصي الحالة والتسليم دون تغيير أي مهمة أخرى. لم تُعدّل DECISIONS أو الخطط التاريخية أو أدلة التطبيق أو الشهادة، ولم تُشغّل أدوات التطبيق/الحذف أو تُفتح معاينة مستضافة.

**الحارس بالاسم والقيمة:** [createSqlAuthoring](../src/features/authoring-review/sql-adapter.ts) يستقبل `assignmentsEnabled = false` افتراضيًا؛ `const actions = assignmentsEnabled ? assignmentActions(...) : undefined`، ثم يضيف العمليات فقط عبر `...(actions ? actions.adapter : {})`. [Session](../src/features/authoring-review/Session.tsx) يعرض قائمة الإسنادات بشرط `adapter.assignments`؛ ويعرض تجهيز الإسناد في SQL بشرط `adapter.assignmentsEnabled === true`. فوق ذلك **لا تستورد أي صفحة في src/app جلسة AuthoringSession أصلًا**؛ نقطة LocalAuthoringReview حاضنة فقط، وتشغيل القبول في [سكربت P2](../scripts/qa/rad-085-p2-sql-audit.mjs) يختار `--assignments` محليًا. تغيير قيمة واحدة لا يصنع مسار منتج.

لا تخلط ذلك مع [P1_AVAILABLE=true](../src/features/supervisor/p1-availability.ts): هو حارس P1 المرتبط بالـmanifest، وقد رُقي فعليًا؛ لا يشغّل P2. شروط جلسة P1: PILOT مهيأ، signedIn، approved، الموافقة العامة الحالية، participant للمشرف مع تعيين خادمي، أو owner للمالك. أما `assess.launch_gate.enabled=false` فهو يمنع **بدء محاولة جديدة** في `start_v1`، وليس السبب في غياب زر الإغلاق؛ لا حاجة لفتحه لإغلاق إسناد. SQL الإغلاق نفسها تشترط `scope_enter_v1(true)` والحساب الفعّال، وملكية/إدارة الإسناد، وللمشرف تعيينًا ومجموعة غير منتهية عبر `supervised_group_v1`.

إذن المستخدم الحقيقي لا يصل اليوم إلى زر P2 من الموقع وفق شجرة التطبيق الحالية. P1 مجرّب هاتفيًا بحسب [إتمام B](RAD-085_P1_B_COMPLETED_2026-10-29.md)، لكن ذلك لا يثبت زرًا لم يُركب. المتبقي: وصل قراءة/إغلاق **المالك أولًا**، ثم المشرف عند وصل P2، مع EN/AR وحالات الصلاحية/revision وغموض ACK وقبول الهاتف. لا حاجة SQL لهذا النطاق، ولا تنسب للمالك سلطة إغلاق أي إسناد عشوائي خارج ملكيته/إدارته.

### حساب السعة ومحفزات المراجعة

الحصتان مستقلتان: **Storage1GB وDB500MB**. نحو3% تعني تقريبًا15MB مستخدمة اليوم إذا كان مقياس Usage نفسه؛ نحو485MB المتبقية ليست كلها ميزانية Assess أو ضمانًا. يجب حجز مساحة Practice والفهارس/TOAST والصيانة ومراجعة Usage الفعلي، ومتوسط/p95 الصفوف تحت حمل مماثل قبل تشغيل حقيقي.

- في M2 خمسة drafts/كاتب،100revision لكل draft، وحجم document≤128KiB: الحد النظري نحو62.5MiB للـrevisions لكل كاتب قبل refs والفهارس والـdraft الحالية. M3 يسمح بحزمة مراجعة≤128KiB لكل revision؛ قد يتضاعف ذلك إلى نحو125MiB/كاتب قبل overhead. أربعة كتّاب عند أقصى الحدود قد يستنفدون حصة DB رغم أن الجداول0 الآن. لا وعد بأن السقوف الحالية تناسب FREE؛ لا تنظيف تلقائي عند انتهاء مجموعة بلا قرار احتفاظ. يوصى بحد تشغيلي أقل وقياس/قرار حذف نسخ غير مرتبطة فقط قبل وصل P2، مع صون المنشور والنتائج والحقوق.
- مثال الكتابي:120طالبًا × امتحانين ×5أجوبة ×4000حرف ×حتى4بايت≈19.2MB نص خام للدفعة، يضاف إليه JSONB والنسخ/receipts والفهارس. يجب تجنب نسخ نص الجواب كاملًا في كل إيصال حفظ. إن كان الحد إجماليًا لكل المحاولة لا لكل جواب يقل الحساب؛ يثبت العقد قبل migration. تُحذف التفاصيل بعد النهائي، أو بعد void يوم7، وفق D4 والمحو؛ لا مصحح يدوي غير محدود العمر.
- مثال الصور:300×250KB≈75MB في Storage، و300×512KB≈154MB قبل نسخ/مشتقات؛ DB تحتفظ metadata فقط. يوصى بتنبيه عند60% ومراجعة عند75% ومنع رفع جديد عند80% المتوقع، مع حفظ مساحة التعافي؛ هذه **عتبات مقترحة غير مطبقة**. لا نعرف استخدام Storage الحالي من نسبة DB3%.
- تُستعاد الصور وmetadata معًا ضمن نسخ RAD-082 المحلية المشفرة؛ قاعدة البيانات وحدها لا تنسخ Storage blobs. لا يفترض أن pg_dump يشمل الملفات أو أن FREE تقدم نسخ مزوّد. اختبار restore يشمل فقد الرابط/الملف وحجر الوصول وإعادة المحو.
- نحتفظ بمقترح RAD-085: تنبيه DB300MB، مراجعة350MB، ومنع امتحان جديد إن توقعت الذروة تجاوز400MB؛ ليس تنفيذًا حاليًا. رفع السقف يحتاج قياسًا واختيار احتفاظ/حصة، أو تمويلًا يوافق عليه المالك، لا purge لبيانات Practice من مهمة Assess. paging20/batch100 والحدود مؤصدرة، ولا أسماء مدرسين/مؤسسات hard-coded. سقف SQL الهاتف يرفعه مسار اللابتوب/CLI في RAD-082، لا تقسيم اللصق وحده.

## 5. الطب والتقييم

لا تغيير في الطب أو المحاكي أو المصحح أو العلامات أو الإصدارات أو hashes/goldens/characterisation. تبقى English لغة المحتوى وEN/AR لغة الواجهة، والتعريض الواحد والتصحيح الخادمي وحجب المفاتيح والسجل المختصر كما قرر المالك. لا نمنح reviewedBy لمن لم يراجع؛ قيد ContentReview الحالي يُحل بتصميم واعٍ قبل النشر، لا ببيانات اصطناعية. أي اقتراح قرب نصّي لا يغير النص الأصلي أو يمنح علامة أو يعتمد إجابة؛ قرار الدرجة للأستاذ.
