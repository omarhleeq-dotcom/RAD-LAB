### 3.2 آلة الحالات: كل الانتقالات والجهة المحركة

`submittedAt` مرجع UTC ثابت: التسليم اليدوي وقت الخادم، وانتهاء الوقت deadline نفسه ولو تأخرت الصيانة. يوم5=`submittedAt+120h` ويوم7=`submittedAt+168h`؛ لا يبدأ عداد جديد عند الآلي أو التصحيح أو الاسترداد أو تغيير المصحح أو إغلاق الإسناد. حد7 شامل: عند `now >= submittedAt+7d` يمنع التصحيح والتثبيت والاسترداد حتى لو تأخر purge. التجربة للمؤقت فقط؛ غير المؤقت يبقى محجوبًا.

| من → إلى | المحرك والشرط والأثر |
|---|---|
| لا محاولة → active | start مصادق، بإسناد ونافذة وموافقة وحد محاولات صالحين وgate مفتوحة؛ نفس حجز المحاولات الحالي. ليست هذه الوثيقة إذن start حي. |
| active → active | الطالب يحفظ جوابه قبل deadline، بعملية/revision؛ المحاكي وحده يحتفظ بقواعد expose. لا تعريض للكتابي؛ تعديل الجواب حتى التسليم فقط، من آخر ACK. |
| active → grading | الطالب submit أو الصيانة/طلب متأخر عند deadline؛ يجمدان آخر محفوظ ويثبتان submittedAt مرة واحدة، ولا يدخل جواب متأخر. |
| grading أو grading-failed → grading | العامل claim_v2 قبل7 مع lease صالح واستحقاق retry. لا يلتقط awaiting-manual؛ لا يعيد الآلي بعد نجاحه بسبب غياب مصحح. |
| grading → awaiting-manual | العامل finish_v2 بعد احتساب أجزاء MCQ/المحاكي من النسخ الخاصة؛ يحفظ نتائجها الدقيقة مؤقتًا ويحرر lease. حتى المحاولة الكتابية كلها تمر هنا، مع مجموع آلي صفر بلا نتيجة نهائية. كل كتابي، ولو فارغًا، يحتاج قرار مصحح صريح. |
| grading → graded | العامل finish_v2 للمحاولة الخالية من الكتابي فقط؛ يستبقي سلوك finish_v1 وحذفه الذري. |
| grading → grading-failed | فشل العامل/انتهاء lease وفق fail_v2 والصيانة؛ لا صفر مصطنع، ولا فتح إجابات الطالب. سياسة retries حتى24ساعة ثم تسوية المالك قبل7 تبقى للمسار الآلي. |
| awaiting-manual → awaiting-manual | مالك أو مشرف مفوض يحفظ/يعدل درجات البنود؛ يرفع gradingRevision فقط. لا lease طويلة للمصحح ولا قفل دائم يحجب المالك. |
| awaiting-manual → graded | manual_finalize_v1 بعد اكتمال كل الدرجات وصلاحية التفويض/revision وقبل7؛ يجمع الآلي واليدوي، ويثبت FinalResult ويحذف التفاصيل ذريًا. هذا وقت الإفراج إن كانت السياسة after-submission. لا انتظار إفراج مستقل بعد اكتمال النهائي. |
| active / grading / grading-failed / awaiting-manual → grading-failed | إجراء الطوارئ المحدث، كما في3.3؛ يلغي leases وعمليات الكتابة المتأخرة ويجمد آخر محفوظ. graded وvoid لا يتغيران. |
| grading-failed → grading-failed، ثم grading أو awaiting-manual | recover_v2 انتقائي بتوجيه المالك قبل7 يزيل hold للتصحيح فقط. إن لم ينجح الآلي، يتيح claim_v2؛ إن نجح مسبقًا، يعيد awaiting-manual دون احتساب الآلي ثانية. لا active ولا تمديد وقت. |
| grading / grading-failed / awaiting-manual → void | maintain_v2 عند7 فقط إذا لم تثبت نتيجة نهائية؛ الدرجات اليدوية المحفوظة دون finalize ليست نهائية. يحذف المؤقت وكل نصوصه، بلا نتيجة أو درجة. انتهاء التعيين أو المجموعة وحده لا يعمل void مبكرًا. |
| graded → محذوفة | صيانة الاحتفاظ عند ستة أشهر تقويمية من submittedAt في UTC، مع clamp اليوم؛ تمنع القراءة فور expiry قبل الحذف الفعلي. |
| void → محذوفة | purge في المعاملة نفسها أو دفعة الصيانة المستحقة؛ لا يبقى نص أو مجموع أو إيصال تجزئة للجواب. |
| أي حالة → محذوفة عند المحو النهائي للطالب | مسار C2/D3 الفعلي بعد نافذته، مع cascades للبيانات الجديدة؛ إلغاء/تعطيل الحساب ليس محوًا نهائيًا. التفاصيل في3.7. |

التكرار بالعملية نفسها لا يصنع انتقالًا جديدًا؛ غير ما في الجدول مرفوض، وبالأخص graded/void إلى active أو انتظار جديد. فشل معاملة manual_score/finalize يعيدها كاملة إلى حالتها السابقة، ولا يحتاج حالة «manual-failed» إضافية. انقطاع ACK يتطلب قراءة receipt/status مفوضة؛ لا إعادة تلقائية بمعرف جديد. إغلاق الإسناد يمنع بدءًا جديدًا ويحفظ إمكانية تسوية المحاولات القائمة دون إعادة فتحه.

### 3.3 D4 وrecover_v1 والتجميد والصيانة

المرجع الحاكم [D4](DECISIONS.md#rad085-owner-tidy-2026-10-27)، مع [قرار RAD-059](DECISIONS.md#rad059-stop-owner-2026-10-29) و[تصميم الإيقاف](RAD-059_OPERATIONS_DESIGN.md) و[التجميد القائم](../supabase/manual/assess-emergency-stop.sql). أسماء anchors تُراجع بالفحص؛ لا يعاد تفسير القرار من تعليق قديم.

يُقترح سجل إنذار أدنى `day5WarnedAt` في manual_work_v1، ينشأ عند submit/expiry أو تجميد active فيها كتابي، حتى لو لم ينجح الآلي بعد: تُحاول قناة التشغيل المعتمدة إنذار المالك ابتداء من يوم5 لكل كتابي غير نهائي، بما فيه grading-failed تحت freeze؛ رسالة بها مرجع محاولة وعدد البنود وموعد7، بلا نص أو علامة. يثبت وقت التسليم للقناة فقط بعد نجاحها، وفشلها يصعّد عبر قائمة التشغيل ولا يسجل «تم الإرسال». إذا استعيدت الخدمة يوم6 تُرسل المتأخرات فورًا؛ عند7 ينفذ void ولا يمدد النافذة لتعويض تأخر التنبيه. إن لم توجد قناة مستلمة ومختبرة فالتصميم غير جاهز لامتحان حقيقي؛ لا إنشاء قناة هنا. المالك يستطيع التصحيح في أي وقت بعد نجاح الآلي وقبل7، وليس عليه انتظار يوم5.

التجميد الحالي يلتقط active/grading/grading-failed فقط؛ **لن يلتقط awaiting-manual**. لذلك لا تكفي إعادة استعمال الأداة حرفيًا. التوصية لعقد RAD059-FREEZE-v2: يضيف awaiting-manual إلى المجموعة المجمدة؛ يحتفظ بـsubmittedAt السابق، وللنشطة يأخذ الأصغر من deadline ووقت التجميد؛ يحفظ الجواب/الدرجات المؤقتة دون تعديلها، ويمسح leases، ويرفع revision، ويضع retryAt عند submittedAt+7d. يثبت `emergencyHeldAt` ضمن بيانات المحاولة المقترحة حتى تعجز عمليات manual والـclaim عن التقدم أثناء hold، حتى مع اتصال حي سابق. تحقق الإيقاف يجب أن يعد awaiting-manual غير المجمدة فشلًا، مع بقاء مهلات lock2s/statement5s وPARTIAL/FAILED وقواعد NOLOGIN/إنهاء الاتصال/تعطيل السر القائمة. لا تعديل درجة نهائية مسجلة ولا void مبكر للنشطة.

[recover_v1](../supabase/migrations/20261020000700_assess_lifecycle.sql) اليوم يضبط retry_at للـgrading-failed قبل7 فقط، ولا يعيد active أو يفتح gate. v2 يحتاج حارس hold وإدراك مرحلة الآلي؛ v1 يرفض محاولة schema2 فلا يتجاوز التجميد. recover_v2 يراجع المالك سبب الفشل ويأذن بتصحيح تلك المحاولة فقط ضمن إجراء الاسترداد المراجع؛ لا يعيد العامل أو الأسرار أو الجداول الزمنية أو الإنفاق تلقائيًا. يحتاج مسار خدمة خاص موثوق يثبت هوية المصحح؛ لا اعتماد assess_worker المستعمل للآلي كهوية أستاذ، ولا اتصال مباشر من الهاتف بجداول خاصة.

[maintain_v1 في retention](../supabase/migrations/20261020001100_assess_retention.sql) يفرغ grading/grading-failed بعد7، ولا يعرف الانتظار الجديد؛ maintain_v2 يضم awaiting-manual وgrading-failed تحت hold وبيانات اليدوي في void/purge. يحكم سباق finalize/void قفل المحاولة وفحص وقت الخادم بعد انتظار القفل وقبل commit؛ finalize الذي تجاوز7 يرفض ولو بدأ قبله. الطوارئ تقفل مجموعة الجلسات كما في العقد الحالي؛ إن سبق النهائي التجميد تبقى graded، وإن سبق التجميد تبطل revision/lease المتأخرة. لا حذف لكل session_details لمجرد نجاح جزء الآلي.

### 3.4 الاحتفاظ بالجواب وحدوده

التوصية `maxAnswerCharacters=4000` لكل جواب، بعدّ Unicode code points متفق عليه بين الخادم والمتصفح، لا UTF-16 code units ولا عدد البايتات. لا trim أو lowercase أو Unicode normalization؛ المسافات والأسطر وحالة الحرف تبقى حرفيًا. تُرفض Unicode غير الصالحة وNUL غير القابل للتخزين دون استبدال صامت؛ يسمح بالأسطر. المحتوى English، وهذا ليس خوارزمية لتخمين اللغة أو إزالة أحرف الطالب. الحد يقترن بحد بايتات الطلب القائم65536 وبسقف كتابي مقترح10بنود/محاولة؛ يحفظ بند واحد بكل عملية، فلا يجمع كل الأجوبة في طلب قد يتجاوز الحد.

الجواب في `session_details.answers` مرة واحدة لكل item/version؛ active يحدّث آخر محفوظ، وبعد التسليم لا يتغير. يربط manual_item_scores_v1 مرجع البند وإصدار answer snapshot دون نسخ النص. يستبقي التجميع الآلي أرقامًا ومراجع فقط في manual_work_v1، بينما تبقى اللقطة الخاصة اللازمة للتصحيح ضمن session_details حتى النهائي. لا نص في events/logs/analytics أو localStorage لصندوق تصحيح؛ المتصفح يعرض صفحة مفوضة واحدة ويمحوها عند انتهاء النطاق/الخروج.

إيصال save يحتفظ operationId وrevision ووقت الخادم والحالة وdigest عابر للطلب فقط، دون answer أو publication أو body. هذا يوافق [session_ack_v1](../supabase/migrations/20261020000700_assess_lifecycle.sql) القائم الذي لا ينسخ الأجوبة؛ لا نجعل إضافة الكتابي تغيره إلى snapshot كامل لكل حفظ. قراءة استئناف منفصلة تعيد آخر محفوظ للمحاولة النشطة فقط. لا نطلب من الخادم حفظ كل ضغط مفتاح؛ حد20000أمر الحالي لا يصبح ميزانية نسخ نص. digests المرتبطة بالجواب بيانات مؤقتة وليست أرشيفًا دائمًا.

| عند7 بلا نهائي | void دون علامة ثم حذف التفاصيل والدرجات والأحداث والإيصالات؛ لا تخزين علامة جزئية لإعادة استعمالها لاحقًا. حجز المحاولات الأدنى يبقى بالقواعد الحالية. |
| بعد ستة أشهر/المحو | حذف النتيجة وتدقيقها الأدنى وreceipt النهائي مع الجلسة؛ reservations حتى إغلاق الإسناد وتسوية جميع محاولاته/نتائجه/استرداده، وconsent حسب سياسة التعطيل القائمة. لا أعمار جديدة لهما. |

سياسة [الاحتفاظ القائمة](ASSESS_RETENTION_POLICY.md) تحذف التفاصيل عند تثبيت النتيجة، لا عند أول مرحلة آلية. اقتراح نص موافقة جديد باسم `assess-written-2026-10-29-v1`، لا تغيير النص تحت v2 ولا قبول نيابة عن أحد: «تُحفظ إجابات الكتابي حتى التصحيح النهائي، بحد أقصى7أيام من التسليم. ننبّه المالك يوم5؛ إن بقيت دون تصحيح نهائي يوم7 تلغى بلا علامة وتحذف تفاصيلها. عند تثبيت النتيجة تحذف الإجابات ولا تعود إعادة التصحيح ممكنة». English: “Written answers are kept until final grading, for at most seven days after submission. The owner is warned on day five. Attempts still awaiting final grading on day seven are voided without a mark and their details deleted. Answers are deleted when the result is committed; regrading is then unavailable.” تراجع الصياغتان والربط/التدقيق الأدنى قبل التنفيذ؛ هذا مقترح إفصاح لا موافقة منشورة.

### 3.5 درجات البنود والتفويض والتنافس

درجة كل كتابي `score` نص decimal بين0 وmaximum المثبت في itemMarks، مع maximum موجب. تطابق [decimalPoints](../src/features/assess/policies.ts): حتى9أرقام صحيحة و6منازل عشرية، لا إشارة أو exponent أو NaN أو فاصلة محلية أو أصفار بادئة عدا0. أمثلة: 0 و1.25 و0.000001 مقبولة داخل حد البند؛ 1.0000001 و-1 و01 مرفوضة. لا floating point، ولا تقريب قبل الجمع؛ نجمع الكسور الدقيقة للآلي واليدوي ونحوّل للسلم مرة واحدة. العرض منزلتان half-up فقط، وتبقى البوابات/المعايير الأصلية للمحاكي دون إعادة توزيع.

المالك المعتمد يدير نطاقه/ما انتقلت إدارته له وفق D3، والمشرف participant بتعيين خادمي لا role عالمي جديد. المشرف يصحح فقط إسناد مجموعته الذي يديره ضمن appointment نافذة صالحة ومجموعة غير منتهية وعضوية/موافقة مشاركة سارية وفق M1/M3/M4. لا تمنح عضوية الطالب الحالية في مجموعة أخرى حقًا في امتحان قديم؛ يلزم assignment_scope وفترة العضوية المثبتة. يفحص التفويض عند القراءة وعند كل كتابة وreplay، ثم بعد الأقفال قبل إعادة نص خاص أو commit. انتهاء المجموعة/التعيين أو سحب الموافقة يسحب وصول المشرف فورًا؛ يتولى المالك التسوية قبل7. لا إعادة عرض cached answers بعد انتهاء visibleUntil. لا اعتماد browser actorId أو groupId كدليل تفويض.

عملية manual_score_v1 تحمل مجموعة درجات محدودة ≤10مع مراجع البنود وexpectedGradingRevision ومعرف UUID للعملية، وسبب مراجعة قصير برمز من `initial`, `correction`, `owner-takeover`. يرفض free text الذي قد ينسخ الجواب إلى audit. هوية مصحح واحدة من الجلسة الموثوقة لكل عملية؛ يمكن أن يسوي المالك بعد مشرف بعملية لاحقة مسجلة، لا مصححان داخل batch واحدة. القفل قصير على المحاولة وترتيب أقفال التفويض متوافق مع D3؛ لا قفل طوال قراءة الأستاذ.

أول عملية صحيحة ترفع gradingRevision؛ منافس بمراجعة قديمة يرفض conflict ويقرأ الجديد دون overwrite تلقائي. تكرار نفس operationId ونفس المعنى يرجع نفس receipt بعد إعادة التفويض، ولا يكرر الحدث؛ إعادة المعرف بمحتوى مختلف ترفض `operation_reused`. digest درجات فقط، لا نص جواب. finalize عملية مستقلة بنفس ضوابط revision/idempotency، تتطلب جميع الكتابي مقيمًا صراحة حتى الفارغ0؛ لا صفر ضمني لبند لم يراجعه الأستاذ. يسمح نفس final operation باستعادة ACK من الإيصال الأدنى بعد حذف التفاصيل، دون إعادة خلق نتيجة.

### 3.6 إعادة التصحيح والتدقيق وما يراه الطالب

التوصية: تعديل درجات البنود جائز قبل manual_finalize_v1 فقط، مع revisions وتاريخ التعديلات؛ finalize نفسه يعني النهائي والحذف والإفراج وفق السياسة. بعده **لا regrade**، حتى لو policy=hidden ولم ير الطالب علامة بعد؛ حذف الأدلة لا يبرر اختراع جواب أو استخراج نسخة احتياطية لإعادة التصحيح. خيار إبقاء نافذة اعتراض بعد النهائي يحتاج تغيير احتفاظ/موافقة مستقلًا؛ ليس افتراض التصميم.

التدقيق المؤقت manual_events_v1 يسجل attemptId وitemRef وoperationId وgradingRevision وgraderId وappointmentRevision/groupScope ووقت الخادم وoldScore/newScore وreasonCode؛ لا answer text أو hash له ولا اسم الطالب في كل حدث. حدود مقترحة100عملية تصحيح/محاولة، مع سماح مستقل لعملية finalize فلا يمنع حد التعديلات تسويتها؛ عند الحد يتوقف التعديل وتُراجع الحالة، لا حذف تاريخ لإخفاء تغييرات.

عند النهائي يختزل إلى manual_final_receipts_v1: attemptId، finalOperationId، expectedGradingRevision للعملية النهائية وfinalGradingRevision، finalizedAt، finalGraderId القابل للمحو، وعدد عمليات/مصححي التصحيح ونتيجة العملية `finalized` وإصدار السياسة. تكفي هذه الحقول لمطابقة إعادة finalize نفسها بلا digest جواب أو نسخة payload. النتيجة الرقمية المرجع الوحيد في FinalResult؛ لا نسخة درجات بنود أو درجات كلية قديمة ولا digests أجوبة. هذا أثر مسؤولية نهائي محدود مع FK للجلسة وexpiry نفسها؛ لا سجل دائم. قبل المحو يستطيع المالك تحديد صاحب التثبيت، ولا يتيح السجل إعادة بناء كل تغيير بعد حذف التفاصيل. اختيار حفظ كامل تاريخ الدرجات يناقش في جدول المالك لأنه يغيّر سياسة حذف تفاصيل البنود الحالية.

| وضع الطالب | العرض والعقد الخادمي |
|---|---|
| active | جوابه الأصلي المحفوظ لإكماله، الوقت وACK؛ لا مفتاح/نموذج حل أو درجات. |
| grading / awaiting-manual / held grading-failed | حالة التسليم فقط: «تم التسليم — بانتظار التصحيح النهائي» / “Submitted — awaiting final grading”، ومع الفشل رسالة استرداد غير كاشفة. لا مجموع آلي أو يدوي أو نسبة/نجاح أو درجات بنود أو نصوص المعايير؛ الحجب في RPC/history/export وليس CSS. |
| graded + after-submission | الحقول الأربعة الحالية: اسم الامتحان، النوع، تاريخ التسليم، والعلامة/المجموع؛ تظهر بعد النهائي اليدوي للمختلط. لا استعراض الأجوبة أو feedback بنود جديد. |
| graded + hidden | السجل المختصر دون علامة كما في السياسة الحالية؛ لا كشف من API مباشرة أو audit. |
| void | «ألغيت المحاولة دون علامة» / “Attempt voided without a mark”، بلا صفر أو مجموع جزئي؛ لا جواب بعد الحذف. |

### 3.7 المحو والتعطيل ونقل الإدارة

طلب حذف الطالب يعطله فورًا حسب C2 ويمنع تفاعله؛ لا يحول الطلب إلى صفر/graded. قبل المحو النهائي تبقى نافذة7 قائمة والمحاولة قابلة لتسوية المالك بحسب الصلاحيات. عند finalise الحساب تُحذف جلساته ونتائجه وكل صفوف اليدوي التابعة لها عبر FK/cascade في المعاملة؛ لا استثناء باسم audit. restore خلال30يومًا لا يستعيد جوابًا حُذف عند النهائي/7 ولا يجدد deadline. سحب مشاركة المجموعة يسحب المشرف ويترك تسوية المالك وفق العقد القائم، دون إعادة تفعيل مشاركة الطالب.

حذف المصحح/المؤلف لا يحذف نتائج طلاب آخرين ولا يغيّر إسناد التأليف إلى المالك. يُنقل تدبير المحتوى/الإسناد والعمل اليدوي إلى المالك **قبل يوم30**، ثم المحو النهائي المعتاد بعد نافذة30 وبحد أقصى7أيام أخرى وفق [O5](DECISIONS.md#rad085-db-day-owner-2026-10-27). تُمحى هويات grader في الصفوف الباقية بـSET NULL/حدث «مصحح محذوف» بلا اسم أو بريد أو UUID مخفي بديل؛ تبقى المسؤولية التشغيلية الحالية للمالك دون نسبة تصحيح تاريخية كاذبة. حقوق إسناد المؤلف داخل محتوى منشور محفوظ تخضع لمصفوفة D3 القائمة، لا تعديل آلي للنصوص/التراخيص. إذا نقلت الإدارة فتفقد handoff digest تغيّر الصفوف؛ يلزم تجديده وفق D3 قبل المحو، لا تجاوز الحارس.

كل FK/جدول جديد يدخل inventory D3 ومراجعة المحو والـreadiness قبل نشر v2، بما فيه ارتباط finalGraderId؛ لا تخفيف حماية الجداول خارج auth أو إعادة استعمال استثناء pins سابق. النسخ المحلية المشفرة7أيام وإعادة الحذف قبل فتح الوصول بعد restore كما في سياسة الاحتفاظ؛ لا نسخ أجوبة للتصدير أو لإلغاء المحو. سجلات Auth المزود بلا FK تبقى سؤال الخصوصية القائم، لا وعد بحذفها هنا.

### 3.8 واجهة «قرب الإجابة» اللاحقة — القرار2

العقد المقترح `TeacherNearMatchSuggestionV1` يتضمن `schemaVersion: 1`, `attemptId`, `itemRef`, `answerRevision`, `gradingRevision`, `candidateRef`, `methodVersion`, `signal`, `limitations`؛ لا حقل score أو accepted أو زر قبول آلي. endpoint المقترح `assess.teacher_suggestion_v1` يتحقق من نفس تفويض manual_read ويستمد الأصل من الجواب الوحيد؛ لا يطلب نسخة من العميل. يعرض الأصل **حرفيًا دائمًا** بجانب الاقتراح، ويستعمل المرجع لإظهار مثال خاص للأستاذ فقط. لا كتابة درجات عند توليد/عرض الاقتراح؛ الأستاذ يدخل الدرجة بنفسه. لا تصل أمثلة الحل/الإشارة إلى الطالب ولا تستخدم للتدريب أو خدمة خارجية بلا قرار منفصل. الاقتراح عابر لا ينسخ النص في audit، ويسقط عند تغير answer/gradingRevision أو انتهاء النطاق.

بعد عمل التصحيح الأساسي فقط يمكن تقييم المرشحين التالية؛ **لا خوارزمية أو عتبة مختارة** في v1:

| المرشح | المنفعة | القيد/الخطر |
|---|---|---|
| مسافة تحرير الحروف | بسيطة ومحلية وتشرح خطأ حرف أو حرفين | تتأثر بالطول؛ النفي أو وحدة القياس قد يقلب المعنى مع فرق صغير. |
| تشابه كلمات/مقاطع حرفية | يفيد ترتيب كلمات مختلفًا، ويمكن تفسير الكلمات المشتركة | قد يخفي أهمية كلمة واحدة؛ التطبيع للمقارنة لا يجوز أن يعدل الأصل المعروض. |
| تمثيل دلالي محلي | قد يساعد مرادفات لا تلتقطها المقارنة الحرفية | كلفة/حجم نموذج وخصوصية وتفسير وانحياز طبي؛ التشابه لا يثبت صحة. |

المصدر والترخيص لا يسقطان بسبب عدم وجود مراجعة طبية؛ licenceNotes ادعاء المؤلف لا إثبات رخصة مستقل، والمصدر غير الواضح يحجب النشر بسبب محدد دون اختراع evidence. MCQ المنشور قديمًا بمراجعة صحيحة يبقى v1 كما هو، ولا تُمحى مراجعات قديمة لإعادة وسمها. ينتج mixed label لكل بند لا reviewed badge عامًا يمحو الفرق. المراجع/الخلفية/الأوزان/المقيّم للمحاكي تبقى مثبتة؛ O108 ومراجعات RAD-063 المستقلة باقية.

الجسر المقترح `verifyAuthoringPublicationV2` يبني سؤال الرافع من revision المخزنة والمفتاح الخاص المتحقق منه، ويربطه بـsourceDigest؛ يتحقق من الحق في التأليف والاسم والمصدر/الرخصة، ولا يستدعي «مراجع مستقل» وهميًا لسؤال عادي. لبنود المحاكي فقط يلزم package مراجع موثوق مع مطابقات case/evaluator/refs والدرجات. المختلط يفشل إذا فقد بند محاكي مراجعته ولو بقية الأسئلة مؤلفة ذاتيًا. تبقى مطابقة draft/revision/digest/install/bind الذرية وقيود التفويض وإعادة القراءة ورفض المجهول كما في الجسر الحالي.

**يحتاج DB day**: M2 يرفض نوع written-answer/حقول v2 وM3 يفرض authoring_reviewed_packages للجميع، وcontent_submit يعيد الحارس داخل SQL. المقترح `assess.authoring_bridge_read_v2` و`assess.content_submit_v2` مع `assess.authoring_provenance_v1` لبيانات منشأ/مراجعة محدودة مربوطة بـdraft/revision/digest دون نسخ publication كامل لكل حفظ. لا تعديل M2/M3 المطبقتين أو تجاوزها من TypeScript. الحزم القديمة تحمى حتى لو اقترح تنظيف revisions غير مرتبطة لاحقًا. نموذج/تصحيح الواجهة وحده في5ب لا يعوض هذا اليوم.

### 4.2 تنظيف النسخ القديمة والتنبيهات

الحفاظ على أحدث3لا يعني حذف القديمة قبل30يومًا لتخطي حد10؛ عند بلوغه سريعًا يوقف حفظ نسخ جديدة ويُفسر السبب. يوصى coalescing تعديلات واجهة غير محفوظة صراحة قبل save، لا إنشاء revision عند كل keypress، ولا إسقاط ACK محفوظة. تنظيف الملفات/الصور وPractice خارج هذا العقد. لا VACUUM FULL آلي أو محو سجلات حقوق لإصلاح الحصة.
