# RAD-085 — اختيار المشرف من دليل المالك، 2026-10-28

## 1. الانحرافات والميزانية

الهدف الوحيد: استبدال إدخال UUID في «تعيين المشرفين» باختيار من دليل المالك مع تأكيد الاسم والبريد، frontend فقط. الميزانية المعلنة17 ملفًا، ثم18 بإضافة إصلاح أداة قبول P1 القديمة لأنها تعتمد الحقل المحذوف. الفعلي18 ملفًا: OwnerDirectory؛ OwnerSupervisorPicker واختباره؛ P1Session وp1-wiring واختبار appointment-read؛ ReviewSession وSupervisorReview وcontracts وsql-adapter؛ رسالتا EN/AR؛ frontend-schema؛ أداتا المتصفح؛ هذا التقرير وHANDOFF وproject-status. لا shared-module خارج هذه القائمة، ولا subagents/worktree.

الاستثناء المسمّى الوحيد للبصمات: **RAD085-OWNER-APPOINT-PICKER-20261028**، بإذن المالك الصريح لتحديث pin حدود المتصفح مع إثبات ثبات marker. لا تعديل لتوقع/بصمة اختبار قائم أو guard؛ أضيف شاهد wiring جديد بنفس السبب.

## 2. المنجَز والمتروك

- حقل UUID أُزيل؛ البحث بالاسم أو البريد والترقيم عبر `owner_account_directory_v1` وبـ`p_status=approved` و`p_limit=20`، من OwnerDirectory نفسه. لا فلترة قائمة كاملة في المتصفح.
- كل مرشح يعرض الاسم والبريد وزر التعيين، ثم تأكيدًا بهما مع Confirm/Cancel؛ Enter وTab وEscape واستعادة التركيز عند الإلغاء. `bdi` والتفاف النص يحفظان RTL والأسماء/البريد الطويلة.
- التعيين يمر عبر `appointment_v1(p_user,true)` في bindP1 الحالي. قائمة التعيينات وRevoke وتأكيده باقية؛ إعادة تعيين الصف الملغى تتم عبر البحث والتأكيد أيضًا.
- أسباب التعطيل: مالك، غير معتمد، معيّن بالفعل؛ انتظار/فشل قراءة التعيين يعطّل الزر. الدليل لا يكشف Terms، فلا نُنشئ أهلية متخيلة أو قبولًا نيابيًا. الخادم يحسم السباق والأهلية؛ رفض denied/conflict يحافظ على النص القائم ويحدّث التعيينات والدليل، دون إعادة mutation تلقائية.
- لم يُنفّذ SQL جديد أو RPC جديد أو تعديل requiredMigrations/checks أو migrations/readiness/CONSENT_VERSION/Terms. لا SQL حي أو Variables أو نشر أو ready/merge/auto-merge أو qa:golden/qa:characterise.

## 3. لكل مهمة

RAD-085 فقط بقيت `review / owner`؛ الوصف والعنوان والمتبقي متسقة مع طلب المالك الحالي: P1 حي، واختيار المشرف ضمن Draft، وفحص الهاتف ومراجعات الأمن/الخصوصية وتأكيد حذف النسخ باقية. دُمج #144 وفق أداة GitHub المتصلة (قراءة مباشرة، لا استنتاج من ref محلي)، وHEAD المحلي يبدأ من merge commit `b59bb40`. لا إغلاق لمهام التشغيل أو الخصوصية بإثبات UI؛ المهام الأخرى لم تتغير. HANDOFF أُعيدت قراءته كاملًا وحُذف انتظار الترقية القديم.

## 4. المشترك وقابلية التوسع S-STD-3

OwnerDirectory يضيف `approvedOnly` اختياريًا؛ مستهلكوه الحاليون يحافظون على مرشح الحالة القائم. ReviewSession يحقن اختيار المالك ويحدّث القراءتين بعد رفض التعيين/الإبطال؛ تغيير الرفض محصور في هذين الأمرين. DTO يضيف قراءة تعيين اختيارية، ويستعملها adapter الحقيقي.

**السقف:** صفحة20 حسابًا، طلب بحث≤100 حرف كما في الدليل، و≤20 طلب حالة تعيين إضافيًا، كل منها `scope_page_v1('appointments',null,UUID-predecessor,1)`. هذا استعمال cursor UUID الحصري القائم لقراءة الهدف فقط، لا مسح صفحات التعيينات ولا تراكم قائمة. تُقارن هوية أول صف بالهدف؛ الجار اللاحق ليس تعيينًا للهدف. اختُبرت حدود صفر/أقصى UUID والانتقال الست عشري وهدف بعد الصفحة الأولى. الصفحات تستبدل القديمة؛ الرد المتأخر يُهمل، وقراءات الحالة تُجهض عند إزالة الصف. ذاكرة المتصفح محدودة بالصفحتين الحاليتين.

تكلفة هذا الحل ≤21 قراءة لكل صفحة مرشحين، إضافة إلى قراءة قائمة التعيينات الحالية؛ لا polling/subscription جديد. رافع هذا السقف مستقبلًا، إذا أظهر حجم الاستخدام حاجة إليه، projection حالة تعيين داخل دليل مجمّع مع اعتماد SQL مستقل؛ ليس مطلوبًا أو مأذونًا بهذه الدفعة. ثنائية اللغة والحدود والأدوار الحالية تُعاد من العقود القائمة، دون قائمة أشخاص/UUID ثابتة في المنتج.
