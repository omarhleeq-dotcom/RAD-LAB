## المتابعة

التالي **RAD-062 Part2: ICU en-US لـP10** وفق [قرار ICU](DECISIONS.md#rad086-icu-owner-2026-10-31). ادمج origin/main إلى فرع P10 القائم دون rebase/force-push؛ أضف ICU en-US بكلا lc=en_US.UTF-8 إلى full-apply M01–M08 والجاهزية بجانب حالتي libc. أي فشل STOP؛ لا تغيير بايتات ترحيل دون إذن. احسب marker واذكر تغيره ضمن تلك الدفعة. نتيجة Supavisor لا تضبط pooler_cache_verified ولا تثبت إلغاء سر العامل؛ اتبع [دليل RAD-059](RAD-059_PHONE_RUNBOOK.md). [قرار اللابتوب فقط](DECISIONS.md#rad086-laptop-only-owner-2026-10-31) ومخاطره ورافع القيد محفوظة.

بروفة Docker worker المحلية بقيت STOP في recovery-gate؛ يلزم نجاحها قبل القبول دون تغيير CI أو اختبار لإخفاء الفشل. التقرير يسجل QA وحدودها.

راجع [براهين P9b](RAD-062_P09B_REPORT_2026-10-30.md) أولًا؛ لا apply حي دون قبولها واستعادة المالك وبروفة PostgreSQL17.11 وبقية STOP. diagnostic ينجح قبل M01 ويفشل بعد M08 بالضبط في الأنواع السبعة؛ الجاهزية تنجح والمنح المتلاعب بها تفشل. B الأصلية على مخطط حالي غير مستعاد تبقى كلها true. لا تغيّر بايتات أو تصنيف required/checks أو marker في P9. كلا packetين ثابت، RAD062_AVAILABLE=false وP1_AVAILABLE=true؛ لا M1–M4/B أو initializer replay.

يوم CLI واحد فقط بعد RAD-086 واللابتوب والنسخة الكاملة المتحقق منها ومسار CLI المراجع؛ أي فشل يوقف اليوم. عند ACK ملتبس لا تعاود التطبيق أعمى؛ استخدم ledger والتحقق المستقل وخطة forward-fix المراجعة. جهز P10 ومراجعتها قبل اليوم؛ نافذة≤60دقيقة من أول M01 COMMIT إلى تحقق P10/attestation والنشر المعتاد، وإلا STOP وخمول وخطة إصلاح مراجعة. فشل B لا يعطل الموقع تلقائيًا لكن M01 قد يرفض أسماء ناقصة قبل name UI؛ لا قبول فجوة مفتوحة. P10 وحدها بعد الدليل الكامل وطوارئ الهاتف لترقية required/checks/guards وحساب marker الحقيقي، يضعه المالك.4ب/5ب والصور والقرب وManage targets والمتابعات المستقلة خارج الدفعة.
