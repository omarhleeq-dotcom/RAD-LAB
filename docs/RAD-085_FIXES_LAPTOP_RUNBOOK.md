# RAD-085 — نافذة اللابتوب اللاحقة

هذه حزمة مؤجلة للمراجعة؛ لا تمنح إذن SQL حي. [التقرير وقرارات النصوص والقيم](RAD-085_FIXES_REPORT_2026-11-02.md#8-قرارات-المالك-الموحدة).

1. قبل النافذة: قيم S1 ونصا P2/P3 معتمدة في [قرار المالك](DECISIONS.md#rad085-owner-approvals-2026-11-02). يلزم مراجعة ترتيب النافذة والرأس النهائي وشواهد PostgreSQL17 بالصورة المثبتة. أبق البوابة مغلقة والعامل NOLOGIN والسر DISABLED.
2. نسخة RAD-086 مشفرة حديثة وبروفة استعادة معزولة على أحدث كتالوج فعلي؛ تحقق جرد الحقوق والمحو وACL. لا تتجاوز أي اختلاف بصمة أو مهلة أو نتيجة UNKNOWN.
3. اتبع [دليل M09](RAD-062_M09_LAPTOP_RUNBOOK.md) حتى حالة ما بعد M09 فقط؛ لا تعِد ترحيلًا مطبقًا. تحقق من ترتيب ملفات الكتالوج الفعلي قبل التنفيذ.
4. طبّق `20261102000200_rad059_emergency_alternate.sql` أولًا كما هي، ثم شغّل `supabase/checks/rad059-alternate-ready.sql`. يلزم نجاح كل صف؛ لا تعيين بديل أو تشغيل عامل ضمن هذه الخطوة.
5. بعد نجاح0200، طبّق `20261102000300_rad085_rights_write_disclosures.sql` كاملة كمعاملة واحدة. preflight داخلها يثبت حالة ما بعد0200 قبل أي كائن جديد؛ لا تنفّذ أجزاء منفصلة.
6. شغّل `supabase/checks/rad085-review-ready.sql` كاملة. هذه successor لجميع R1/R2/S1/P2/P3، وتشمل كتالوج Assess وemergency وواجهات pilot المتأثرة. يلزم كل `ok=true`؛ لا تعِد تشغيل ready القديمة التي تثبت أجسام الدوال السابقة بعد0300.
7. لا تغيّر marker أو manifest أثناء SQL. PR ترقية لاحقة منفصلة تحدّث الحراسة وrequiredMigrations وsuccessor checks وإثبات الخدمة معًا؛ النصوص المعتمدة ونسختا موافقة Assess/Terms تُنشران معها في الترقية المنفصلة. حسابات الاختبار تعيد قبول v3 شخصيًا؛ v2 لا تمنح التصحيح.
8. اختبر بحسابات اصطناعية: المحجوب يبقى مرئيًا ويطلق alert؛ الآخرون يُمحون؛ انتظار قفل يتجاوز نهاية المجموعة يرفض القبول؛ الملاحظات والأحداث والمحاولات تظهر رسالة الحد؛ هوية الطلب محصورة في الاسم ومعرف الطلب.
9. راجع القنوات وACK والإبطال وفق [RAD-059](RAD-059_ALTERNATE_LAPTOP_RUNBOOK.md) منفصلًا. إشعار SQL `rad085_erasure_blocked` مجمع بلا هوية؛ ليس إثبات تسليم تنبيه خارجي أو ACK بشري.

## المتابعة اليومية دون تمديد

شغّل `supabase/checks/rad085-erasure-health.sql` يوميًا بقراءة المالك: أعمار≥25/30/35/37 يومًا تراكمية، وحقوق غير محلولة وتنبيه≥25. أي خطأ/timeout = UNKNOWN يتطلب متابعة، لا نتيجة سليمة فارغة.

سوِّ الحقوق وانقل الإدارة **قبل30**. بعد30 شغّل finalise يوميًا حتى إتمام المحو≤37؛ لا تغيّر requested_at أو أي مهلة. الحساب المحجوب يبقى في قائمة الطلبات مع الموعد الأصلي، وSQL تعيد معرفه ورمز الخطأ وتطلق WARNING وNOTIFY مجمعًا.

كل نداء محدود بمئة حساب فحص كحد أقصى، ويدعم `p_after`/`next` مرتبين بالـUUID. عند ظهور «قد تبقى حسابات أخرى» اضغط finalise مرة أخرى؛ الناقل يحتفظ بالمؤشر في الذاكرة بين النداءات الصريحة. بعد نهاية المرور يبدأ المرور التالي من البداية لإعادة محاولة المحجوب. لا يُحفظ المؤشر أو معرف المحجوب في تخزين المتصفح.

لا يعني نجاح حسابات أخرى إغلاق حالة المحجوب. التحذير وقائمة الإدارة والفحص اليومي يظلان مطلوبين؛ راقب الإشعار بالقناة المعتمدة ولا تفترض أن NOTIFY يصل وحده إلى الهاتف. فشل COMMIT/timeout لا يعطي إيصال نجاح؛ أعد القراءة والمصالحة قبل متابعة المالك.

## حدود الاسترجاع

لا rollback حي تلقائي ولا تخفيف للحراس؛ تحتفظ بالنسخة ودفتر RAD-086 وتبقي الخدمة مغلقة عند فشل أي فحص. لا تُعد تطبيق0200 بعد0300؛ preflight القديمة ستتعمد رفض الكتالوج الجديد. بعد استعادة نسخة سابقة، أعد قواعد المحو والمصالحة والتحقق قبل أي فتح وفق الدليل القائم.
