## 3. حسب المهمة

**RAD-069 C1:** تنفيذ للمراجعة في المسودة؛ حارس الاختبار صُحح بالاستثناء ونجح؛ يحتاج تطبيق SQL/إثبات المخطط ومراجعة المالك. أجزاء A/B السابقة وحدودها محفوظة؛ لا إغلاق للمهمة كلها.

**RAD-044 — التحقيق:** SQL الحالية ترشح الملاحظة بتاريخ `feedback.at` وفحصها، وتربط المحاولة بـLEFT JOIN لا بصفحة المحاولات؛ لا حاجة لتحميل المحاولات كلها. تفاصيل الملاحظات القديمة تمرر مرشحات التصدير نفسها. قائمة الحسابات القديمة تتجاهل التاريخ عمدًا بينما التصدير يستخدمه، وصفحة متابعة التدريب كانت بمرشحات مستقلة؛ جمع هذه الوظائف في صفحة واحدة يفسر الالتباس ولا يثبت سبب حذف صف بعينه.

العيب البرمجي المؤكد: input يوم محلي أُرسل بلاحقة Z، فصار يوم UTC. الآن يُحوّل بدء اليوم المحلي إلى UTC، ونهايته إلى آخر microsecond قبل منتصف الليل المحلي التالي (حتى عبر DST). اختبار SQL اصطناعي يعيد حالة 17–24: ملاحظة الساعة00:30 محليًا يوم17 تُنتج CSV بلا صفوف بالحد القديم وتظهر بالحد المصحح؛ ويختبر نهاية24 واستبعاد25 وملاحظة مرتبطة بمحاولة خارج المدى وتساوي أعداد الشاشة والتصدير. يختبر يوم DST بطول25ساعة أيضًا.

**حد الإثبات:** لا سجل طلب أو بيانات حية لواقعة المالك، فلا نثبت أن المنطقة الزمنية كانت سبب الملف الأصلي، ولا نجزم بمرشح فحص أو تاريخ الملاحظة. تبقى RAD-044 review حتى يتحقق المالك من الملاحظات القائمة والعدد/CSV محليًا دون إرسال بيانات. الطلب الحالي يؤرخ الواقعة2026-10-22، والحالة السابقة تؤرخها2026-10-24؛ اختلاف محفوظ في القرار لا تاريخ مختلق.

## 4. المشتركات وScale

`owner_dashboard_v1` إضافة قراءة للمالك المعتمد فقط، search_path ثابت وقيم مربوطة وEXECUTE صريح ورفض anon. الحد20 صفًا مع keyset cursor؛ المنتظرون ثم المعتمدون ثم الموقوفون، وUUID داخل الحالة. أعداد الحالات تراعي بحث الاسم/البريد؛ تغيير الحالة أثناء التصفح ليس snapshot، ويُستعمل تحديث الصفحة لرؤية الوضع الحالي. ملخص الفحوص20 فحصًا/صفحة، وأكثر خمسة بنود خاطئة لكل فحص؛ العدد الكامل للمحاولات لا يُختزل إلى صفحة العميل.

لا تعديل لبايتات `owner_page_v1` أو الترحيلات القديمة. فرع attempts الجديد يغلف القراءة القائمة ويضيف comparison_version المحفوظة للصفحة نفسها فقط؛ لا يشتقها من settings أو الدرجة. بيانات الإصدار غير المعروفة تمنع الرسم وفق حارس المقارنة القائم. على المخطط السابق تظل النتائج والفئات مقروءة، لكن الرسم محجوب لأن RPC القديمة لا تشهد metadata المقارنة. العرض20 سجلًا؛ التصدير القائم1000 سجل لكل جزء، تنزيل صريح لكل جزء مع حد القراءة وتقرير اكتمال/تخطي؛ الذاكرة لا تجمع كل الحسابات أو المحاولات. ملف CSV يحتفظ بالصيغة القديمة وبحماية الصيغ وبالرمز بدل البريد/UUID؛ النص الحر يبقى كما كتبه صاحبه وفق سياسة الخصوصية القائمة.

**المخطط الحالي:** فقط عند missing-RPC (`PGRST202`/`42883`) يستعمل الدليل بحث training القائم20 صفًا، ثم تفاصيل bounded لكل صف، مع HEAD counts بلا صفوف. يزور الحالات بالتتابع ليبقى المنتظرون أولًا؛ قد تظهر صفحة حالة فارغة قبل التالية. الأعداد في هذا المسار عامة وموسومة بذلك؛ الملخص الجديد يوضح انتظار التطبيق، والملاحظات والمحاولات والتصدير تعمل بالدالة القائمة. لا سقوط صامت إلى قراءة الكل عند خطأ صلاحيات/شبكة.

**سقف الأداء:** fallback حتى21طلب بيانات +3HEAD لكل صفحة؛ رفعه بتطبيق الترحيل، لا بتحميل الجميع. بحث substring وعدّ/تجميع من الخادم قد يفحصان عددًا كبيرًا من السجلات؛ عند نمو زمن الاستجابة يلزم قياس وفهارس بحث/تجميعات مخزنة وفق الاستخدام، دون توسيع حجم صفحة المتصفح. سجل الفحوص واللغات والصلاحيات القائم هو المرجع؛ لا معرفات مشاركين ثابتة في المنتج.

**حفظ Assess التاريخي:** المولد كان يبني الحزمة القديمة من latest، فأدخل RPC الجديدة وغيّر نص preinstall وبصمته رغم أن Assess لم يتغير. أصبح المرجع يطبق F ثم retention المحدد؛ تظل قاعدة الاختبار الحالية latest، وتظل المقارنة تسمح بدوال public الإضافية وفق القاعدة الأصلية. اختبارات الكتالوج عادت للنجاح وبصمة preinstall الأصلية `186ea18a…0c6359c` محفوظة؛ لا تعديل pins أو تطبيع مصدر مجهول.

## 7. المفتوح وتصميم الحذف — لا تنفيذ

الحذف المقترح يحذف حساب Auth وملف profiles ومحاولات Practice والملاحظات والأحداث المرتبطة. يلزم جرد علاقات Assess (التكليفات والعضويات والمحاولات وقيود الاحتفاظ) قبل تحديد ما يحذف أو يحجب أو يبقى؛ لا يُفترض أن CASCADE يكفي. العميل الساكن لا يملك صلاحية إدارة Auth. يلزم RPC أو خدمة خادم للمالك المعتمد فقط بترحيل جديد، search_path ثابت وصلاحيات صريحة، رفض حذف النفس وآخر مالك، ومعاملة ذرية حيث تسمح خدمة Auth، واختبارات RLS/رفض غير المالك والتزامن والفشل والآثار التابعة. لا مفاتيح إدارة في المتصفح.

تُراجع الإضافة ضمن schema gate وsource pins وreadiness checks؛ attestation جديدة للمشروع المحدد بعد تحقق المالك من SQL والخدمة، دون تخفيف الحارس. يعرض التأكيد البريد والنطاق والعدد ثم يطلب كتابة البريد كاملًا وإعادة تأكيد نهائي، مع بيان أن النسخ الاحتياطية قد تبقى حتى انتهاء احتفاظ المزوّد. تُراجع نصوص الخصوصية والاحتفاظ وحق المحو وبيانات Assess والنسخ؛ لا وعد بمحو فوري شامل.

**أسئلة قرار المالك:** هل الحذف نهائي أم تعطيل ثم مهلة؟ هل يشمل Assess أم يحفظ سجلاته حسب سياسة الاحتفاظ؟ ما المهلة وسياسة النسخ وسجل التدقيق الأدنى الذي لا يعيد هوية الشخص؟ **يتوقف هذا البند هنا بلا تنفيذ.**

**حارس الاختبار:** [AGENTS](../AGENTS.md) تمنع تعديل توقعات قديمة إلا باستثناء محدد. عُرض الفرق أولًا، ثم أجاب المالك «نعم، أضف الدالة الجديدة للحارس فقط»؛ [القرار](DECISIONS.md#rad069c-test-exception-2026-10-24). نُفذ العدد والاسم فقط ونجح الحارس؛ لا قرار آخر مطلوب لهذا البند.

## 8. قائمة المالك والمتابعة

1. مراجعة التبويبات والكثافة على الهاتف، والبحث عن حساب خارج الصفحة الأولى وتبديل الحالة والإجراء الرئيسي والتفاصيل، ثم Back والرابط `?tab=training` و`?tab=assess`.
2. الاستثناء الضيق للحارس تم بموافقتك ونجح؛ لا توسيع له إلى أي توقع أو hash آخر، ولا إعادة QA الكاملة تلقائيًا.
3. خطوات SQL الدقيقة والتحقق والماركر في [دليل Supabase §C1](PILOT_SUPABASE_SETUP.md#owner-dashboard-c1): الترحيل الجديد وحده، فحص الجاهزية المقروء، تحقق المصدر وصلاحيات الجلستين، ثم حساب شهادة المشروع وتحديثها يدويًا بعد الدليل. لم ينفذ الوكيل أي خطوة حية.
4. تحقق من CSV الملاحظات القائمة لمدى17–24 بالتوقيت المعروض والفحص المختار؛ طابق العدد مع الشاشة محليًا. عند اختلاف، أرسل فقط وصفًا منقحًا للمرشحات/المنطقة وعدد المطابقة/المكتوب/المتخطى دون أي صف أو اسم أو بريد أو رمز. لا إغلاق RAD-044 قبل التحقق.
5. حسم أسئلة تصميم الحذف في §7؛ لا إذن تنفيذ ضمن C1. يبقى Assess مؤجلًا خارج إعادة التنظيم الحالية، ولا جاهزية تشغيل أو نسخة/استرداد جديدة مثبتة.

**سؤالا AGENTS:** هل تغير الحكم عند التلخيص؟ لم تُختصر قاعدة قديمة؛ أُضيف تفصيل C واستثناء محدد مأذون لحارس الدوال فقط، مع حفظ الحدود والتجميد. هل بقي رابط الدليل الأصلي؟ نعم: قرار C يحيل إلى قرارات تقسيم RAD-069 والجرد الأصلي، وأدلة pilot السابقة باقية؛ اختلاف تاريخ واقعة RAD-044 وحدود إثبات السبب مذكوران صراحة.


**نص الجلسة التالية المقترح:** اقرأ AGENTS وdocs:context للـPR المسودة وstatus:summary لـRAD-069 وRAD-044، ثم تقرير C1 وقرار استثناء الحارس. تابع ملاحظات المالك على الهاتف ونتيجة تطبيق SQL/التحقق إن أرسلها؛ لا تتصل بمشروع حي ولا تعِد ترحيلات أو QA ناجحة بلا تغيير ذي صلة. حافظ على بقية A/B والحذف تصميمًا فقط حتى قرار مستقل.

## متابعة deferred DB — قرار المالك 2026-10-24

1. **الميزانية/القرار:** هذه المتابعة على PR #126 نفسها بميزانية15ملفًا، وتنفذ [قرار DB day](DECISIONS.md#rad069-deferred-db-day-2026-10-24). لم يتغير ملف الترحيل أو readiness SQL ولا كود الحارس؛ تفاصيل QA تضاف عند اكتمالها.
2. **المنجز/المؤجل:** عادت قوائم المتطلبات إلى مخطط main المثبت. محول RPC الجديد معزول خارج الواجهة، وتستعمل مسارات البحث/الحالات/الترقيم/الملاحظات/التصدير الحالية مباشرة. الملخص يعرض انتظار التحديث. كل SQL مؤجلة مع C2 (الحذف والاستبيانات لاحقًا، لا تنفيذ لهما الآن).
3. **المهام:** C1 للمراجعة على الهاتف دون اشتراط SQL الآن؛ تبقى ملاحظة RAD-044 أعلاه: المالك يفحص CSV لمدى17–24 على الهاتف بعد النشر، وسبب الواقعة الحية غير مثبت.
4. **المشتركات وScale:** تصنيف deferred ببصمة وحدود غير قابلة للوصول من client؛ لا استثناء أو تجاوز للحارس. تجاوز أقسام حالة فارغة بحد أقصى3قراءات بحث، وتفاصيل حتى20صفًا و3HEAD counts؛ لا تحميل كل المشاركين. اختبارات الحارس القديمة تحتفظ بتوقعاتها وتستخدم عينات مخططها التاريخي؛ الاختبار الجديد يحمي تصنيف C1 وتأجيلها والشهادة الحالية.
5. **الطب/التقييم:** لا تغيير للتقييم أو الصور/المشاهد أو الثيم أو البصمات.
6. **QA:** لم يكتمل بعد. رفض GitHub قراءة متغير Actions مباشرة بـ403؛ لا إعادة أو تجاوز. اختبار الحارس يستعمل القيمة الحالية **الموثقة** في دليل retention، والمشروع العام الموثق ومفتاحًا عامًا اصطناعيًا؛ لا اتصال بقاعدة أو قراءة سر، ولا ادعاء قراءة القيمة البعيدة الحالية.
7. **المفتوح:** لا إجراء SQL أو تغيير شهادة الآن. تبقى أسئلة الحذف في §7 وخطة C2 للمراجعة، ولا يُستأنف Assess أو يفتح runtime.
8. **المالك/المتابعة:** الهاتف وCSV الآن بعد النشر؛ [خطة DB day](PILOT_SUPABASE_SETUP.md#owner-dashboard-c1) لاحقًا: المعلق المعتمد بالترتيب → كل فحوص الجاهزية → ترقية المتطلبات ووصل الواجهات → شهادة واحدة جديدة. **سؤالا AGENTS:** تغير توقيت التطبيق/اشتراط النشر بقرار المالك؛ روابط القرار السابق ودليله محفوظة، ولم يتغير نطاق الحذف أو التقييم.
