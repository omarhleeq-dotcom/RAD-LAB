# RAD-078 — بوابة الموافقة بعد تسجيل الدخول

## 1. الانحرافات والميزانية

الهدف: منع أي محتوى تطبيق عند حاجة الحساب المسجل إلى الموافقة، وإظهار تنبيه للمحاولة غير المحفوظة وحالتي feedback المطلوبتين. الميزانية المعلنة17ملفًا، ثم18بإضافة لوحة مراجعة مضغوطة واحدة، ثم19لحفظ نية استعادة كلمة المرور في SessionProvider أثناء حجب الحساب، ثم21بعد إضافة المالك لحالتي feedback. التنفيذ في checkout المعزول نفسه، بلا subagents أو worktree. لم يتغير اختبار قائم أو browserBoundaries أو SQL أو CONSENT_VERSION.

كشف الفحص أن فرضية «تدريب الزائر بلا حساب» تخالف سياسة SessionGate الحالية. صحح المالك البند2 صراحةً بتاريخ2026-10-25: إبقاء سياسة الوصول واختبار session-access.test.ts؛ الخروج يعيد مسار الزائر/الحساب الحالي. لم يُوسّع الإصلاح لفتح التدريب للزائر. بيانات main تحمل وقت حالة متقدمًا على ساعة البيئة؛ رُفع وقت الحالة ثانية واحدة عن السابق للحفاظ على ترتيبها، ولا يُقدّم كدليل توقيت تحقق حي.

إثبات السبب بإفادة المالك (2026-10-25): مشارك approved بموافقة قديمة لديه25محاولة محفوظة؛ محاولة جديدة ناجحة لم تُحفظ؛ بعد قبول Terms من الحساب حُفظت المحاولة التالية فصار العدد26. هذا تحقق المالك الحي، لا فحص مباشر من الوكيل.

## 2. المنجز والمتروك

بوابة خارج AppShell لكل صفحات اللغتين، تستخدم needsConsent والحساب المشترك. أثناء تحميل الحالة تظهر رسالة التحميل القائمة وحدها. pending/approved/suspended والمالك مشمولون؛ AccountPanel الحالية لا تستثني دورًا. القبول يستدعي acceptTerms الحالية نفسها: تحديث عمودَي profiles؛ ليست RPC مستقلة في الكود الحالي. لا تنقل البوابة المستخدم، فيبقى المسار والاستعلام والجزء؛ بعد إزالتها تسري سياسة الوصول الأصلية.

استُخرج ConsentPrompt ليُستخدم في AccountPanel والبوابة، ونص Terms إلى TermsContent مشترك؛ النص كامل قابل للقراءة داخل البوابة حتى لا يصبح رابط Terms محجوبًا دون وسيلة قراءة. فشل القبول يبقيها، وزر الخروج يستخدم الإجراء القائم. يمنع تعطيل الأزرار تعارض القبول والخروج المتزامنين.

ملاحظة «لم تُحفظ هذه المحاولة» تظهر للمشارك المسجل في عرض النتيجة متى لم تؤكد savedAttempt الحالة saved، بما في ذلك null/pending/unavailable؛ تزول عند saved. لا تغيير لمحرك النتيجة أو تسجيل المحاولة. لا استعادة تلقائية لمحاولة ضاعت سابقًا. نية رابط استعادة كلمة المرور/خطئه محفوظة في الحساب المشترك قبل التحميل؛ تصل إلى AccountPanel حتى إن استُهلك الجزء قبل ظهورها، ثم تُستهلك النية مرة واحدة فلا يعود نموذج الاستعادة عند زيارة الحساب لاحقًا.

في feedback يرى المشارك الذي لا ينتظره استبيان: «لا يوجد استبيان حاليًا. شكرًا لك — سنخبرك عند فتح استبيان.» ويرى المالك أن المشاركين يجيبون عن الاستبيانات، مع رابط محلي إلى لوحة المالك. قارئ الاستبيان الحالي باقٍ ولا يُستدعى للمالك. رسالتا EN تطابقان نص المالك. C2Session مثبتة ولم تتغير.

## 3. حسب المهمة

RAD-078 فقط أضيفت review بانتظار المالك؛ العمل مسودة غير مدموجة. RAD-069 وبقية مهام الهاتف وAssess والطب والمصادر تبقى بمتبقيها، ولا يُستنتج نشر من دمج #131.

## 4. الوحدات المشتركة وScale

التغييرات المشتركة محصورة في layout، AccountPanel، عرض SimulationWorkspace بإضافة الملاحظة، وTermsPage وSessionProvider (حفظ جزء رابط الاستعادة قبل أن يستهلكه Supabase) وصفحة feedback ومكوّن FeedbackContent مع المكونات الثلاثة الجديدة. jsdom اعتماد تطوير لاختبارات DOM. لا حساب آخر أو قراءة بيانات جديدة أو كتابة لكل مستخدم أو حد حجم. لا قائمة أدوار مستثناة أو معرّفات صفحات للبوابة؛ جميع الصفحات تحت layout. اللغات من النظام القائم. أعداد فقرات Terms هي القائمة القائمة نفسها؛ إضافة فقرة مستقبلًا تستلزم تحديثها كما قبل الاستخراج، بلا حد جديد.

## 5. الطب والتقييم

لا تغيير طبي أو في scoring أو منطق simulator أو scenes أو result engine/state/images أو hashes أو golden/characterisation. جميع الوحدات المثبتة في browserBoundaries وmanifest والترحيلات والفحوص SQL وconsent.ts بايتاتها ثابتة.

## 6. التحقق

- الاختبارات المرتبطة الأولية:54ناجحًا في5ملفات، تشمل غياب/قدم الموافقة، موافقة حالية، خروج، تحميل، جميع الحالات والأدوار، القبول والعودة لنفس الرابط، فشل القبول، حالات ملاحظة الحفظ. تعثر typecheck عند توسيع مساعد الاختبار الجديد لقبول ParticipantSurvey؛ ضُبط نوع محتواه إلى ReactNode ثم نجح.
- بعد حماية الاستعادة:49اختبارًا ناجحًا في3ملفات؛ وبعد إضافة feedback:40اختبارًا في4ملفات، منها حالتا المالك/المشارك وعدم وجود استبيان. لا تعديل لتوقع قائم.
- إثبات الحدود: دالة SessionGate نفسها مطابقة بايتياً لـorigin/main؛ manifest وكل ملف مثبّت في browserBoundaries مطابق، ولا تعديل لأي ملف اختبار قديم.
- إثبات الاستخراج: HTML Terms مطابق بايتياً لصفحة origin/main: EN6432بايت، AR8744بايت، باستخدام renderToStaticMarkup لكلتا النسختين.
- تدقيق المتصفح النهائي:412تحققًا و32axe ناجحة، منها حالتا feedback ×اللغتين×العرضين×الثيمين؛ لا violations أو overflow أو أخطاء صفحة أو طلبات خارجية. تضمّن التحقق نموذج الاستعادة بعد استهلاك fragment وقبول الموافقة. تشغيل flow-only إضافي للنسخة النهائية من سياق الحساب:36تحققًا ناجحًا. أصلحت أداة التدقيق محدد نموذج reset-form، وإغلاق ورقة الحالة بالمساعد المشترك قبل تدقيق نتيجة الهاتف؛ لا تعديل للمنتج لمعالجة QA.
- التصدير الساكن مع PILOT مفعّل بمفتاح publishable اصطناعي نجح: `npm run build:pages`؛ فُحص HTML المرئي لكل43صفحة لكل لغة قبل hydration، فوجدت رسالة التحميل القائمة دون محتوى التطبيق. نجح البناء العادي أيضًا قبل إضافة feedback؛ دليل البناء النهائي هو التصدير المفعّل بعد الإضافة.
