# RAD-085 — PR A: قابلية استخدام P1 بعد اختبار الهاتف

## 1. الانحرافات والميزانية

الهدف: إصلاح قابلية استخدام واجهتي المشرف والطالب مع ثبات SQL والخصوصية. الميزانية المعدّلة15 ملفًا: وحدتا ReviewSession/SupervisorReview، كتالوجا EN/AR، أربعة اختبارات، تدقيق المسارات، أربع وثائق ولقطتان. لا تغيير requiredMigrations أو checks أو ترحيل مطبّق أو درجات أو hashes طبية. أسباب تعديل الاختبارات مسمّاة P1-USABILITY-F1/F3/F6/F7 وF6-EXPIRY؛ لم تتغير توقعات الصلاحيات والنتائج.

## 2. المنفّذ والمؤجّل

بطاقات مجموعات ذات تاريخ إنشاء وانتهاء ومرجع يميّز الأسماء المكررة، فتح أول مجموعة تلقائيًا، أقسام الطلبات/الطلاب/النتائج/الإعدادات وروابطها، تلميح اختيار بدل قائمة طلبات فارغة، وإرشاد إنهاء المجموعة المنشأة بالخطأ. أعداد الطلاب للمنتقاة من total الموجود؛ الطلبات من الصفحة فقط مع تنبيه حين توجد صفحة تالية. لا جلب لكل المجموعات لحساب شارات.

لوحة الرمز تبقى في الذاكرة عبر التحديث حتى «تم»، مع نسخ وتأكيد وWeb Share ونسخ بديل. بقية أوامر المجموعة معطلة حتى إغلاق اللوحة حتى لا يبدّل أمر ثانٍ الرمز؛ مغادرة الصفحة/إخفاؤها أو إبطال النطاق يمحو البيانات وفق حارس الخصوصية القائم. لا تخزين محلي أو URL أو بريد.

الطالب يرى خطوات الموافقة ثم الرمز ثم حالة الطلب، وشرح الفرق بين المغادرة وسحب الموافقة. في A اسم المجموعة/الشخص يستخدم فقط البيانات الموجودة؛ ما لا يتوافر يظهر بتسمية محايدة. إرجاع الأسماء والرمز القصير يحتاجان PR B.

## 3. بحسب المهمة

RAD-085 تبقى review؛ أفاد المالك بنجاح الخطوات12 على الإنتاج بحسابَي اختبار، وتشمل التعيين بمنتقي #149، إنشاء مجموعات، الموافقة والانضمام والقبول ورؤية التدريب والسحب الفوري والإنهاء والإبطال. هذه إفادة المالك وليست SQL حيًا من الوكيل. تحقق GitHub المباشر أثبت دمج #149 بتاريخ2026-10-28.

F6: بعد نجاح end/leave/revoke يمسح Session التحديد ومؤشرات الصفحات قبل القراءة التالية، ويعرض النجاح. فشل الطلب أو فقد ACK يبقى خطأ ولا يُعاد تلقائيًا. اختبارات الواجهة الثلاثة تثبت عدم قراءة المجموعة القديمة؛ اختبارات منع عرض الاستجابات المتأخرة باقية.

## 4. المشترك وScale

`useAccount.signUp` يرسل `raw_user_meta_data.display_name`؛ مشغّل `handle_new_user` في ترحيل التدريب يكتبه في `profiles.display_name`. لا اختلاف full_name/display_name في مسار التسجيل الحالي. الاسم الثلاثي إلزامي في واجهة التسجيل الجديدة؛ التحقق الخادمي قاعدة قديمة مفتوحة في RAD-062. العضو القديم قد يملك display_name=null، والمُهيّئ كان يستبدله بالـUUID؛ العرض يعالجه الآن بتسمية محايدة. الطلبات والتدريب لا يقدمان الاسم في SQL الحالي. لا قراءة auth.users ولا ترحيل أسماء أو بريد بديل.

S-STD-3: كل صفحة RPC20 عنصرًا مع UUID keyset؛ لا مسح/تراكم قوائم أو اشتراكات أو polling. الأعداد متاحة للمنتقاة فقط. سقف المجموعة1000 عضو وطلب الرمز10 محاولات/ساعة/حساب كما هو؛ رفعهما يحتاج قياس الحمل ومراجعة الحماية. رمز A يبقى64 hex؛ يغيّره B. الأسماء المحايدة مرقّمة داخل الصفحة وليست هوية ثابتة. الهاتف اليدوي محدود بقاعدة [النقل](DECISIONS.md#rad085-mobile-sql-owner-2026-10-28)، ورافعه RAD-082.

## 5. الطب والدرجات

لا تغيير طبي أو حساب درجات أو فحوص أو مشاهد أو صور تشخيصية. المجموع المعروض محفوظ دون إعادة تقييم. نصا موافقة المشاركة وإصدارهما مطابقان للأصل؛ لا إضافة بريد.

## 7. المفتوح

مراجعة المالك للواجهة على الهاتف بعد اختياره دمج A؛ B يتطلب mini DB day منفصلًا قبل ضبط علامته. لا إغلاق RAD-059/RAD-082 أو مراجعات الأمن/ACL والقبول والخصوصية القديمة. لا حذف مجموعات أو سجلات؛ الإنهاء يؤرشف حسب السياسة.

## 8. قائمة المالك وبرومبت المتابعة

راجع بطاقتين بالاسم نفسه، طلبًا معلّقًا، نسخ/مشاركة الرمز ثم «تم»، إنهاء مجموعة خطأ، والمغادرة/السحب ورسالة النجاح. أبقِ A وB Draft حتى قرارك؛ اضبط علامة B فقط بعد SQL والجاهزية والدخان الموصوفين في حزمته.

برومبت: «اقرأ AGENTS وHANDOFF وتقريري A/B؛ افحص Git/CI مباشرة دون polling. تابع مراجعة الواجهة وحزمة mini DB day؛ لا SQL حي أو Variables أو نشر يدوي أو ready/merge من الوكيل».

**سؤال AGENTS الأول — هل تغيّر الحكم؟** لا حكم قديم اختُصر أو أُلغي؛ سُجل طلب المالك الحالي ونطاقه، مع بقاء قاعدة الهاتف والخصوصية.
