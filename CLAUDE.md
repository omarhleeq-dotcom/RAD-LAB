# CLAUDE.md — RAD-LAB development guide

RAD-LAB is a bilingual (AR/EN) educational radiography simulator. Source of truth: `docs/RAD-LAB_Project_Specification.md` — **read it before large changes**. Work in small, focused sessions; do not build unrelated features (no auth, DB, CT/MRI, 3D, physics until the spec says so). **Exception — pilot slice only (owner decision S-PILOT-2/4, 2026-10-15):** accounts and a Postgres database (Supabase) for the pilot's saved Practice attempts, usage events and notes (`docs/PILOT_PLATFORM_PLAN.md`); no Assess, organisations, payments or grading.

## Rules
1. **Do not invent medical facts.** Unvalidated clinical values must be marked provisional (`provisional: true`, TODO comments) and never shown as authoritative. Never fabricate diagnostic radiographs; result visuals are labelled placeholders until validated imagery exists.
2. **Exams and cases are data.** An exam (controls, rules, tolerances, scoring weights, critical findings, technique protocol, scene/render bindings) is an `ExamDefinition` in `src/data/exams/*`; one patient scenario on it (patient, order text, baseline, cooperation, attenuation, initial state) is a `CaseDefinition` in `src/data/cases/*`. `composeCase()` yields the `RadCase` compat view the engine/UI consume. No per-case pages or hard-coded case logic in components. Validate new definitions with `validateExam` / `validateCase` (tested in `features/exam`).
3. **Keep modules separate.** `domain/` (types) ← `features/evaluation|scoring` (pure logic, no React) ← `stores/` ← UI. Simulation logic must not live in React components.
4. **Bilingual always.** UI strings go in `messages/en.json` + `messages/ar.json` (keep keys in sync); case text uses `LocalizedText` with both locales. Use logical CSS (`ms-`, `ps-`, `border-s-`), keep numbers/units `dir="ltr"`, test both directions.
5. **Scoring weights are configuration** (`ExamDefinition.scoring`), must sum to 100 (tested by `validateExam`).
6. Prefer reusable components; avoid unnecessary dependencies and global state.
7. Practice mode exists; keep the design Assessment-ready (no help/answers leaked in assessment) and instructor-ready.
8. Document significant architectural decisions in README or `docs/`.
9. **Scale-ready by default (S-STD-3, owner 2026-10-16, binding).** Build nothing without a proven need, but every feature or addition must leave room to grow and must not create a ceiling: before adding it, state in the PR what limit it could create (data volume, hard-coded value sets / ids / locales / roles in code or schema, schema or payload shape without a version, unindexed or unbounded reads, per-user write limits, a change that can only be applied by hand) and how it avoids it. Prefer data and configuration over hard-coded sets, versioned shapes, bounded + paged reads (keyset, server-side) and an additive path for the next exam / modality / mode / language / role / organisation. This is not licence for speculative features (rule of three still applies): it means the foundation never blocks the next one. A needed ceiling is allowed only if recorded as an open decision with the trigger that lifts it.

## Before finishing a task
`npm run check` (typecheck + lint + tests) and `npm run build` must pass; exercise the flow in a browser in both `/en` and `/ar`.

## Session continuity (Codex, owner instructions 2026-10-11)
- At the start of each new conversation, read `docs/HANDOFF.md` and the previous session record, then only the references and decisions needed for the selected goal. Verify the actual branch, HEAD and working tree; the handoff is a summary, not authority to override `DECISIONS.md` or the current owner prompt.
- Keep one focused goal and an explicit change budget per session. Follow S-STD-1 QA by session type; a docs-only session needs Markdown checks, not an application build. Do not repeat successful QA without a relevant change or unresolved failure.
- At each phase boundary, update `docs/HANDOFF.md` with completed and unfinished work, exact branch/base, QA run and not run, blockers and the next action. Keep detailed history in the session documents and update `ROADMAP_SESSIONS.md` when a phase's status changes.
- Send owner-facing updates and final reports in Arabic. Use the S-STD-1 eight-section order for execution reports, and finish each phase with a ready-to-copy prompt for the next conversation.
- Create a draft PR for review when changes are ready. Never merge it or enable auto-merge; the owner merges manually. Report a blocked or uncreated PR accurately. This supersedes the owner's earlier request not to create PRs.
- Each Codex cloud task is already isolated: use its existing checkout; do not create a Git worktree unless the owner explicitly requests one.
